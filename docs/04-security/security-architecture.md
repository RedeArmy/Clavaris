# Security Architecture — Clavaris

✅ Aprobado (2026-08-28) — SDE-III review confirmed no substantive blocker remained: `threat-model-stride.md` §6's own gap list is clean except MFA, explicitly risk-accepted for v1. First document promoted out of `🟡 En revisión` in this project's history (TD-PROC-002), on the recommendation named across four prior reviews. Every future edit to this document should re-open review status only if it introduces a real, unresolved gap — not reset to `🟡` reflexively on every routine update.

## 1. Scope

This document describes how Clavaris protects the credentials and tokens it is solely responsible for issuing and verifying. Unlike JobSeeker (which delegates this entire concern to Clavaris — see JobSeeker's own `docs/04-security/security-architecture.md` §1-2), this *is* the system of record for authentication, so this document carries the full weight that JobSeeker's no longer needs to.

## 2. Credential storage

- Passwords: Argon2id (ADR-0005), never logged, never returned in any API response, never stored anywhere in plaintext including in-memory longer than the single verification call requires.
- Client secrets: hashed at rest, same principle as passwords (`data-model.md` §2).
- Tokens (refresh, verification, authorization codes): only their hash is persisted; the bearer value exists only in transit and on the holder's side (`data-model.md` §2). **TD-SEC-019 (closed):** `oauth2_authorization` — the table backing Spring Authorization Server's own `JdbcOAuth2AuthorizationService` (TD-SEC-003) — now follows the same hash-only rule too. SAS's own `findByToken` lookup compares against the stored column directly with no supported way to hash on write and still support that lookup natively, so a wrapping `HashedTokenOAuth2AuthorizationService` (`app` module) HMAC-SHA256-hashes every authorization-code/access-token/ID-token value before it reaches `JdbcOAuth2AuthorizationService`, restoring the raw value in memory only for the exact token slot SAS's own revocation/introspection providers immediately re-compare it against. A Postgres compromise no longer exposes these tokens directly usable, only their keyed digest — matching every other token table this project controls the schema for.

## 3. Token signing and key management

- RS256, asymmetric (ADR-0002) — private key never leaves Clavaris, never stored in the application database (`data-model.md` §2). **TD-SEC-002 (closed):** `TOKEN_SIGNING_KEY_STORE_PATH` now actually backs a PKCS12 file (`SigningKeyStore`, identity-module) holding every key's real material, aliased by `kid` — a process restart reloads existing keys instead of unconditionally generating fresh ones, so a routine deploy no longer mass-invalidates every issued token for every tenant.
- **Per-`Organization` since ADR-0010 §5**: each tenant has its own key pair, its own issuer (`{clavarisBaseUrl}/o/{organizationId}`, path-based), and its own `/oauth2/jwks` document — a signing-key compromise is a single-tenant incident, not a Clavaris-wide one. The Spring Authorization Server extension needed to serve per-tenant JWKS correctly is validated and live (ADR-0003's addendum, spike 0001 — **GO**), built directly on those findings.
- Keys rotate with overlap: a new key becomes active for signing while the previous key remains published until every token issued under it has naturally expired, so no consumer ever fails verification mid-rotation. v1 rotation is a manually-triggered, audited management-API operation per Organization (ADR-0010 §5.2), not a scheduler-driven job — that's v1.1. **TD-SEC-008 (closed 2026-08-23):** real, self-service rotation with real overlap — `POST /api/v1/admin/organizations/{organizationId}/signing-keys/rotate`, cryptographically live-verified (`SigningKeyRotationIntegrationTest`) that a pre-rotation token still verifies against the post-rotation JWKS. See `incident-response-signing-key-compromise.md` §3 for the real containment procedure and §6 for what's genuinely still open (TD-SEC-029 — no emergency zero-overlap purge for a confirmed compromise, only the routine overlapping rotation).
- Key-compromise incident response: `incident-response-signing-key-compromise.md` — written against the current implementation, which does not yet have the per-tenant rotation endpoint ADR-0010 §5.2 describes; the runbook's own §6 documents that gap explicitly rather than assuming it away.
- `PlatformClient` bootstrap-credential compromise (the highest-value credential in the system, ADR-0010's Organization-provisioning tier) has its own separate runbook, `incident-response-platform-client-compromise.md` — writing it surfaced a new, previously untracked gap: no self-service way exists to revoke or rotate a `PlatformClient` at all today, only raw SQL against production (TD-SEC-018).

## 4. Rate limiting

Bucket-based rate limiting (mirroring JobSeeker's own Bucket4j + Redis approach, ADR-0011 there — not yet formalized as its own ADR here, but the same technology choice is expected). Since ADR-0010 §6, this is two layers, not one:
- **Anti-abuse (fixed, system-defined, never tenant-configurable)** — `/login` and `/oauth2/token`, keyed by `(organization_id, account_or_ip_identifier)`, tuned against credential stuffing, distinct (tighter) thresholds than a generic API rate limit (BR-ID-06). No tenant can loosen this, even in v1.1.
- **Capacity ceiling (per-`Organization` aggregate, operator-managed in v1)** — keyed by `organization_id` alone, protects one tenant's traffic from exhausting budget shared with unrelated tenants (`RateLimitPolicy`, ADR-0010 §6.2). Tenant self-service is v1.1, gated on audit logging shipping first.
- registration and verification-email resend — tuned against email-quota exhaustion, same two-layer principle applies if this ever needs per-tenant tuning (not yet a concrete requirement).
- **Management API (`/api/v1/admin/**`), closed 2026-08-26 (TD-SEC-030).** A third layer, structurally simpler than the two above since this surface has no browser callers at all — every caller is a backend service authenticated via a platform-tier Bearer token. `AdminApiSecurityConfig` wires its own `AntiAbuseRateLimitingFilter`, keyed by the authenticated `client_id`, not IP. A blanket per-client ceiling across the whole surface, plus much tighter ceilings specifically on `POST .../accounts/*:delete` and `POST .../organizations/*:delete` — the two operations where a runaway or compromised client does irreversible damage fastest, §7/§7a below.

**Every tunable threshold above, by its real property name and current default value — TD-PROC-003, closed 2026-08-28**: `app/src/main/resources/application.yml`'s own `clavaris.rate-limit.*` block is the single source of truth (each value there previously existed only as an inline Java `@Value(...:default)`, undiscoverable without reading source across four config classes). Not duplicated here on purpose — a second copy of the same numbers would drift the moment one side is tuned and the other isn't. An operator can read or override any of them the normal Spring Boot way (edit the file, or set the equivalent `CLAVARIS_RATE_LIMIT_*` environment variable).

## 5. Transport and headers

- TLS required for every environment beyond local development — no exceptions for the OIDC surface, since tokens and authorization codes in transit are the entire attack surface PKCE and RS256 are designed to protect against.
- Standard security headers: `Strict-Transport-Security`/`X-Content-Type-Options`/`X-Frame-Options` come from Spring Security's own zero-config defaults (verified, no gap). `Content-Security-Policy` on the hosted login/consent UI is real and implemented (TD-SEC-009, closed 2026-08-24) — `ContentSecurityPolicyHeaderWriter` (`app`), content-type-gated so it only ever applies to actual HTML responses: a strict policy (`default-src 'self'`, no inline script/style, no external hosts) for every template this project owns, and a narrowly-scoped relaxed one specifically for Spring Authorization Server's own default consent page (one named CDN host, `'unsafe-inline'` only for scripts — that page's own real, external requirements, confirmed by decompiling SAS's `DefaultConsentPage`). Investigating that page's own real needs originally surfaced that it never actually rendered — closed 2026-08-25, see below.
- **Consent, per-client, secure by default (TD-SEC-026, ADR-0017, closed 2026-08-25).** `oauth_clients.require_consent` defaults `true` for every registration; `OrganizationRegisteredClientRepository` wires it straight into `ClientSettings.requireAuthorizationConsent(...)`, so SAS's own `DefaultConsentPage` now genuinely renders (live-verified end to end — approval issuing a real, tokenizable code, and a declined consent redirecting with `error=access_denied` and no code, `AuthorizationCodeFlowIntegrationTest`). An operator opts a trusted first-party client (JobSeeker's own registration) out explicitly via `requireConsent: false` — never inherited by omission. The consent screen itself is still SAS's unbranded default (TD-SEC-011, narrowed 2026-08-28) until ADR-0009's embedded/branded login work happens — clickjacking/XSS posture reviewed and confirmed adequate for a page this project doesn't own the source of: `X-Frame-Options: DENY` (Spring Security's own zero-config default, confirmed no `.frameOptions(...)` override exists anywhere) plus this same page's own `frame-ancestors 'none'` CSP directive (above) double-cover clickjacking, and its `'unsafe-inline'` script allowance is scoped as narrowly as SAS's own `DefaultConsentPage` genuinely requires (one named CDN host, confirmed by decompiling that class — see `ContentSecurityPolicyHeaderWriter`'s own Javadoc), not a blanket relaxation. What's left in TD-SEC-011 is only per-client branding/display-name/logo/custom-domain, which is real net-new work this project doesn't have a page to own yet — genuinely gated on ADR-0009, not a review gap.
- **CORS: deliberately none, on any endpoint (ADR-0013).** v1 supports confidential OAuth clients only — every `OAuthClient` requires `client_secret_basic` in addition to PKCE, enforced by `OrganizationRegisteredClientRepository`/`PlatformRegisteredClientRepository` unconditionally, with a dedicated regression test on each asserting no code path can ever produce a public/PKCE-only client. There is no legitimate cross-origin browser caller for `/oauth2/token` or any other endpoint, so a CORS allowlist would only ever be attack surface (a misconfigured origin entry leaking a token exchange) with no corresponding capability behind it.

## 6. Logging and observability

- Structured JSON logs for every authentication event, with credential/token values never included (BR-DATA-01) — full detail in `docs/01-product/nfr-quality-attributes.md` §5.
- Refresh token reuse-detection firing is treated as a security signal worthy of alerting, not just logging (`nfr-quality-attributes.md` §5) — this is one of the few events in the system that indicates an active, not just potential, compromise.

## 6a. Session revocation (tenant `Account` tier) — closed 2026-08-26

**TD-SEC-031.** Every "revoke everything for this account" call site — `ConfirmPasswordResetService` (BR-ID-04), `RotateRefreshTokenService`'s reuse-detection cascade (BR-ID-03), and both deletion services in §7/§7a below — already revoked the SAS-managed access/ID token and this project's own `Session`/`RefreshToken` rows, but none of them touched a live `HttpSession`, if a browser happened to still hold one in Redis at that moment (`DistributedSessionConfig`, `maxInactiveIntervalInSeconds=1800`). The `PlatformAccount` tier already had the correct pattern (`PlatformAccountSessionRevokerBridge`, `SessionRegistry.expireNow()`); the tenant `Account` tier's own interactive chain (`OrganizationAuthorizationServerConfig`) simply never wired the same capability in, despite already depending on the same Redis-indexed session infrastructure.

Closed with a new `AccountSessionRevoker` port/bridge, an exact mirror of the platform-tier pattern, called from all four sites above (the organization-wide deletion case revokes every owned `Account`'s session individually, via a new `AccountRepository.findAllByOrganizationId` read). **`expireNow()` alone was not sufficient** — `OrganizationAuthorizationServerConfig` had no `ConcurrentSessionFilter` wired at all before this fix, so marking a session expired in the registry had no enforcement point that ever checked it.

Getting the enforcement wiring right took two real, live-caught regressions before it was correct, not one: Spring Security's own default expired-session handling is a terminal response, wrong for a chain whose own login page is `permitAll()` (a stale-but-cookied browser couldn't even reach the login page at all) — fixed with `InvalidateAndContinueSessionExpiredStrategy`, which invalidates the stale session and continues the request as fresh-anonymous instead. That fix alone then broke a *second*, unrelated thing: `ConcurrentSessionFilter`'s own `doLogout()` step clears `SecurityContextHolder` unconditionally whenever it finds an expired session, and on this chain's own actual filter order (confirmed with real Spring Security `TRACE` logging, not guessed), SAS's `OAuth2TokenEndpointFilter` sits *after* the generic `.anyRequest().authenticated()` check — so a stale, unrelated browser session cookie riding along on an otherwise-correct, Basic-Auth-authenticated `/oauth2/token` refresh-token call was enough to get it redirected to the login page instead of processed. `RefreshTokenRotationIntegrationTest`'s own reuse-cascade assertion caught this live. Fixed with `TenantSessionConcurrencyFilter`, which wraps a real `ConcurrentSessionFilter` but skips it entirely for this chain's own machine-authenticated SAS endpoints (`/oauth2/token`/`introspect`/`revoke`/`jwks`/`.well-known`/`userinfo`) — deliberately **not** exempting `/oauth2/authorize`, since a stale session there ending up redirected to login is the actual desired outcome, not a bug to route around.

## 7. Account deletion (management API) — built, live-verified

**Shipped 2026-08-26** — closes the last real gap `roadmap-and-release-plan.md` §2's own three-unbuilt-v1-capability list named (alongside social login and `Workspace`, both still unstarted). Requested explicitly, framed correctly from the start: a hard external dependency for JobSeeker's own ADR-0013, not a speculative feature, with a scope already this narrow and already this well-defined — nothing exotic to design.

`POST /api/v1/admin/accounts/{id}:delete` (BR-DATA-02, `DeleteAccountController`, identity-module), gated by its own `platform:accounts:delete` scope, same defence-in-depth posture as every other admin-API mutation. Consuming applications (e.g. JobSeeker) call this once their own local data-handling process (grace-period-then-anonymize, ADR-0013 there) completes. On call:

| Step | Action |
|---|---|
| 1 | The account's SAS-managed access/ID tokens (`oauth2_authorization`) are revoked immediately (`AccountTokenRevoker`) |
| 1a | Any live `HttpSession` for this account is revoked immediately (`AccountSessionRevoker`, §6a above, closed 2026-08-26) |
| 2 | Every `WorkspaceMembership` row referencing this Account is erased (`WorkspaceMembershipEraser`/`WorkspaceMembershipEraserBridge`, closed 2026-08-27 alongside the Workspace feature — ADR-0007) |
| 3 | *(not yet applicable — see below)* |
| 4 | The account record itself is hard-deleted (BR-DATA-03) — cascades at the database level (migration `V20260826100000`) to `password_credentials`/`sessions`/`refresh_tokens`/`verification_tokens`, every table whose only reason to exist is this one `Account`'s own data |

**Step 2, closed 2026-08-27**: before `Workspace` existed there was nothing for this step to act on; it now genuinely erases every `WorkspaceMembership` row for the deleted Account, synchronously, in the same transaction, before the `account.deleted` outbox event is raised — `WorkspaceIntegrationTest` proves it against real Postgres. Step 3 (delete `SocialIdentity` links) remains **not applicable today** — social login is still genuinely unbuilt (zero code, per `roadmap-and-release-plan.md` §2). `DeleteAccountService`'s own Javadoc names this as an obligation to revisit the day it ships, not a silently-dropped requirement.

Clavaris does not run its own independent grace period for this — the calling consumer owns that policy decision; Clavaris treats the call as final. The multi-consumer-identity caveat (one account shared across two consumers) **is resolved by ADR-0010**: `Account` is scoped to exactly one `Organization` (one consuming system's isolated account pool), so a deletion request against one Organization's account can never reach an identity another consumer depends on — that scenario no longer exists by construction, not by policy. See `business-rules.md` BR-ORG-01/03 and `domain-model.md` §8.

Live-verified end to end, not just wired: `DeleteAccountIntegrationTest` runs a real Authorization Code exchange first (so a real, Account-bound `oauth2_authorization` row genuinely exists), deletes the account, then confirms — against real Postgres, not mocks — that the account row, its `password_credentials` row, and its `oauth2_authorization` rows are all actually gone; that the deletion is audited (`account.deleted`, `audit_events`); and that the exact same credentials that worked a moment earlier now fail login identically to any never-registered account (anti-enumeration, no distinguishing signal). Also proves 404 on an unknown account and 403 without the required scope.

## 7a. Organization deletion (management API) — built, live-verified

**Shipped 2026-08-26**, the same day as §7 above — BR-DATA-02/03's own organization-level equivalent: "delete this entire consuming system's account pool, not one identity within it." No pre-existing design section named this as planned scope before it was requested — unlike account deletion, this was genuinely new, discovered to have zero code (not even a stub) when investigated.

`POST /api/v1/admin/organizations/{organizationId}:delete` (`DeleteOrganizationController`, organization-module), gated by its own `platform:organizations:delete` scope — the single most destructive operation this management API exposes, deliberately separate from `platform:accounts:delete` (defence-in-depth: a token that can delete one Account can't also delete an entire Organization). On call:

| Step | Action |
|---|---|
| 1 | Every SAS-managed token this Organization's Accounts or OAuthClients ever obtained (`oauth2_authorization`) is revoked immediately (`OrganizationTokenRevoker`) — must run first, its own subqueries need the rows step 2 erases to still exist |
| 2 | Every `Account` this Organization owns has its live `HttpSession` revoked (`AccountSessionRevoker`, §6a above, closed 2026-08-26), then is itself erased (`OrganizationIdentityDataEraser`) — cascades (migration `V20260826100000`, identity-module) to each one's own `password_credentials`/`sessions`/`refresh_tokens`/`verification_tokens`; every `SigningKey` it ever rotated through is erased alongside it, same port |
| 3 | Every `OAuthClient` it ever registered is erased (`OrganizationOAuthClientsEraser`, client-registry-module) |
| 4 | The `Organization` record itself is hard-deleted — cascades at the database level (migration `V20260826110000`, organization-module, same-module) only to its own `rate_limit_policies` |
| 5 | An `organization.deleted` domain event is written to organization-module's own outbox (`EventOutboxWriter`, closed 2026-08-26, TD-ARCH-007) — functionally inert until `webhook-module` exists to drain it, same posture as every other outbox write in this codebase |

**Erasure is application-layer for steps 2–3, not a database-level cascade** — a deliberate departure from account deletion's own approach. A cross-module FK (identity-module's `accounts`/`signing_keys`, client-registry-module's `oauth_clients`, all referencing organization-module's `organizations`) was tried first and reverted: each module's own Testcontainers-backed test suite only scans its own `db/migration` folder, so a migration in one module referencing another module's table fails that module's own isolated tests, even though it passes a combined, full-`app`-context verification. `data-model.md` §2 records the same finding against each affected column. Real, load-bearing lesson for this codebase: cross-module referential integrity must be enforced at the application layer, via ports + `app`-module bridges (the same pattern `SigningKeyProvisioner`/`CreateOrganizationSigningKeyBridge` already established for the *creation* side of this exact module boundary), never via a DB-level FK.

Live-verified end to end: `DeleteOrganizationIntegrationTest` builds one real row in every table an Organization owns — an Account with a genuine Authorization Code exchange (so a real `oauth2_authorization` row exists), an OAuthClient, the auto-provisioned SigningKey, a RateLimitPolicy — then deletes the Organization and confirms every one of those rows, and the `organizations` row itself, is actually gone from real Postgres, that the deletion is audited (`organization.deleted`, `audit_events`), and that a rejected request (missing scope) deletes nothing. Also proves 404 on an unknown organization.

**No `Workspace`/`WorkspaceMembership` application-layer erasure step exists here — none is needed.** Both tables live in organization-module, same module as `organizations` itself, so `workspaces.organization_id`/`workspace_memberships.workspace_id` both carry a real, same-module `ON DELETE CASCADE` FK (migration `V20260827130000`/`V20260827130001`) — they cascade away for free the moment step 4 deletes the `organizations` row, the same free-cascade precedent `rate_limit_policies` already established. `WorkspaceIntegrationTest` proves this against real Postgres too.

## 7b. Workspace management (management API) — built, live-verified

**Shipped 2026-08-27** — closes the Workspace row `roadmap-and-release-plan.md` §2 has named as the last unbuilt v1 capability with real design weight (social login is the other zero-code row, out of scope here). ADR-0010 §3's addendum records the v1 scope decision this closes: two-role membership (`ADMIN`/`MEMBER`, no `OWNER`), members provisioned directly (no invitation), business/product roles explicitly out of scope.

Six endpoints under `/api/v1/admin/organizations/{organizationId}/workspaces` and `/api/v1/admin/workspaces/{workspaceId}/members`, same platform-tier-only posture as every other admin-API surface. Three new dedicated scopes (`platform:workspaces:write`, `platform:workspace-members:write`, `platform:workspace-members:remove`) — the same defence-in-depth "not just any valid platform token" posture `AdminApiSecurityConfig` already applies to every mutating admin-API action; the two read (`GET`) endpoints require only a valid platform token, no dedicated scope, matching every other listing endpoint on this surface.

**Adding a member is the one genuinely new security-relevant mechanism**: `POST .../members` provisions a brand-new `Account` (a real write into identity-module, via the `AccountProvisioner` port/`WorkspaceMemberAccountProvisionerBridge`) with a `SecureRandom`-generated password that is never returned, logged, or retained past the call, then immediately reuses the already-built, already-audited password-reset-request flow so the new member sets their own real password via a real emailed link. No new credential-issuance path, no new mail template — 100% reuse of `RegisterAccountUseCase`/`RequestPasswordResetUseCase`. This endpoint carries its own tighter rate-limit rule (`admin-api-workspace-members-write:client`, default 60/5min) since, unlike most admin-API mutations, it triggers a real outbound email — same "side-effect-bearing endpoint gets its own ceiling" precedent as the `:delete` endpoints.

**BR-WS-01's replacement invariant** (at least one `ADMIN` per Workspace at all times) is enforced at the application layer in both `ChangeWorkspaceMemberRoleService` and `RemoveWorkspaceMemberService` — a demotion or removal that would leave zero `ADMIN`s is rejected with `409`, verified live (`WorkspaceIntegrationTest.rejectsRemovingTheLastAdminOfAWorkspace`).

**BR-WS-03, stated honestly**: v1 has no workspace-scoped token/authorization concept — removing a member is immediate in the sense that the admin-API listing and the `workspace_membership.removed` outbox event fire synchronously with the delete, not in the sense that a live token is invalidated (none exists to invalidate; tokens remain Account/OAuthClient-scoped per Organization). A consuming application gating its own authorization by workspace membership must re-check membership itself, or subscribe to the outbox event once `webhook-module` exists. **Partially closed by §7c below** (BR-WS-06, 2026-08-27): a role change now reaches the consumer on the member's next login or next silent token refresh, without any webhook — still not an instantaneous revocation of an already-issued, still-valid token, but materially better than "no signal until the consumer separately polls."

Live-verified end to end (`WorkspaceIntegrationTest`, real Postgres, real HTTP, real mail-sender mock): create workspace → add member (real Account row + real password-reset-email trigger, both asserted) → change role → remove member; the last-ADMIN guard on both role-change and removal; the duplicate-email 409; the unknown-workspace 404; and both cascade obligations this feature closed (§7's `WorkspaceMembershipEraser` on Account deletion, §7a's free DB cascade on Organization deletion).

## 7c. Workspace-role login signal (`workspace_id`/`workspace_role` claims) — built, live-verified

**Shipped 2026-08-27**, same day as §7b — closes the real gap in how a consuming application (e.g. JobSeeker) was supposed to know, at login time, whether a given user should see its own admin panel. BR-WS-06: `WorkspaceRoleClaimsCustomizer` (`app` module, composed into `OrganizationAuthorizationServerConfig`'s own `JwtGenerator` customizer lambda alongside `TokenIssuanceEventLogger`/`AuthenticationContextClaimsCustomizer`) adds `workspace_id`/`workspace_role` to both the ID token and the access token for the interactive Authorization Code flow, for any Account with a Workspace membership — omitted entirely for the overwhelming majority of Accounts that have none.

**A real, live-verified gap closed along the way, not assumed**: Spring Authorization Server's own default `/userinfo` mapper (`OidcUserInfoAuthenticationProvider$DefaultOidcUserInfoMapper`, decompiled via `javap` against the actually-resolved 7.1.0 jar, same discipline TD-SEC-028's own investigation used) reads claims from the ID token, then silently drops anything outside an explicit allow-list (`sub` plus the standard `address`/`email`/`phone`/`profile` claim groups, scope-gated) — a custom claim like `workspace_role` never reached `/userinfo` under that default, confirmed by a failing assertion before the fix, not by inspection alone. Closed by `WorkspaceAwareOidcUserInfoMapper`, wired via `.oidc(oidc -> oidc.userInfoEndpoint(...))`: faithfully reproduces the default's own scope-gated filtering for every standard claim group (so nothing already-conformant regresses the day this codebase actually populates `email`/`phone`/`profile` claims), and adds `workspace_id`/`workspace_role` unconditionally on top, since BR-WS defines no dedicated OIDC scope for them.

No caching layer — one extra Postgres read (`WorkspaceMembershipRepository.findAllByAccountId`) per authorization-code issuance or refresh, the same "don't build a caching layer before real traffic justifies one" call `RateLimitPolicyRepository` made until its own read was actually cached (TD-FUT-012, closed 2026-09-02) — this read has had no comparable traffic-driven trigger yet, so it remains uncached, on its own merits, not by leaning on that row as an active precedent any more.

Live-verified end to end (`WorkspaceRoleClaimIntegrationTest`, real Postgres, real HTTP, a real Authorization Code + PKCE exchange): a real workspace member's ID token and `/userinfo` response both carry the correct `workspace_id`/`workspace_role`; a regular (non-member) Account's ID token carries neither claim at all.

## 7d. Reversible account suspend/ban (management API) — built, live-verified

**Shipped 2026-08-27**, same day as §7b/§7c — BR-ID-08: `POST /api/v1/admin/accounts/{id}:suspend` / `POST /api/v1/admin/accounts/{id}:reactivate` (`SuspendAccountController`/`ReactivateAccountController`, identity-module), gated by a single shared `platform:accounts:suspend` scope (suspend/reactivate are symmetric and reversible, much lower stakes than `platform:accounts:delete`'s permanent hard delete — same "grouped under one scope for same-risk-tier actions" precedent §7b's own `WORKSPACE_MEMBERS_WRITE` scope already established).

`SuspendAccountService` reuses the exact same revocation ports `DeleteAccountService` already calls (`AccountTokenRevoker`/`AccountSessionRevoker`) — a ban kills an already-live session/token immediately, not merely block future logins. Future logins are already covered by an existing check: `AuthenticateWithPasswordService` rejects any non-`ACTIVE` account before touching the password hash at all (same anti-enumeration shape as every other rejection there — a generic re-rendered login form, never a distinguishing status code), so suspension needed no new login-time gate, only the state transition itself. `ReactivateAccountService` reverses it with no revocation step (un-blocking is not blocking). Both transitions are audited (`account.suspended`/`account.reactivated`) and written to identity-module's own outbox.

Live-verified end to end (`AccountSuspensionIntegrationTest`, real Postgres, real HTTP, a real Authorization Code exchange first so there's a real, Account-bound `oauth2_authorization` row to prove gets revoked): suspension revokes that row immediately, blocks a subsequent login attempt with the exactly-correct password, and is audited; reactivation restores login. Also proves 404 on an unknown account (both directions) and 403 without the required scope.

## 8. Dependency and supply chain

Standard practice expected (not yet formalized as an ADR): automated dependency vulnerability scanning in CI, consistent with what JobSeeker's own CI/CD pipeline is expected to run. No divergent policy needed here.

## 9. External review gate

Non-negotiable: no consumer sends real user traffic to Clavaris until an external security review finds zero open critical/high findings. This document, `threat-model-stride.md`, and the known-gaps list in both are the primary inputs to that review — closing the gaps listed in `threat-model-stride.md` §6 (corrected 2026-08-28 — this reference pointed at §5, "Lessons from Clerk's disclosed CVEs," a threat/test table, not the actual gap list) is a precondition for scheduling it, not something to be discovered during it. As of 2026-08-28, §6's own gap list is clean except for one explicitly risk-accepted item (MFA absence, deferred to v1.1 per `prd-mvp.md`) — every other gap that section ever named is resolved. `risk-register.md`, `incident-response-plan.md`, `access-review.md`, `vendor-management.md`, and `asset-inventory.md` (TD-FUT-016) are secondary inputs — the organizational/governance layer an ISO 27001/SOC 2 readiness review would also expect, distinct from this document's own technical-control scope.
