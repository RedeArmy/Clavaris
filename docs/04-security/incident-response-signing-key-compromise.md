# Incident Response Runbook — Per-Organization Signing Key Compromise

🟡 En revisión

Closes TD-SEC-005 / `threat-model-stride.md` §6's "no incident-response runbook for signing-key compromise." Written against the system as it actually exists today — every step below is checked against real, currently-merged code, not the eventual ADR-0010 §5.2 design nor a stale memory of an earlier implementation. **Corrected 2026-08-26**: the previous revision described a raw-SQL-and-restart procedure that stopped being accurate the moment TD-SEC-008/TD-SEC-010 closed (2026-08-23) — it sat wrong for three days before being caught, on direct challenge rather than a routine review. §6 still lists the real gaps that remain.

## 1. Scope and severity

Covers a suspected or confirmed compromise of one `Organization`'s RS256 private key material (`SigningKey`, ADR-0010 §5). **P1** (`threat-model-stride.md` §2's own severity for this row) — serious, but by design (ADR-0010 §5) scoped to one tenant, not the whole system. Contrast with the `PlatformClient` runbook (`incident-response-platform-client-compromise.md`), which is higher severity precisely because it isn't scoped to one tenant.

**Trigger conditions** — any of:
- Key material found somewhere it shouldn't be (committed to a repo, exposed in a log despite BR-DATA-01, found on a paste site, present on a compromised host).
- `/o/{organizationId}/oauth2/jwks` serving a key (`kid`) that doesn't correspond to any row this Organization's own `SigningKey` metadata tracks.
- A token verifies successfully against a tenant's JWKS that this Organization's own `event=token_issued` logs (TD-SEC-016) have no matching record of ever issuing.
- The affected consuming application reports unexplained account activity consistent with forged tokens.

## 2. Detection

- `event=token_issued` / `event=token_revoked` logs (TD-SEC-014/016/017), filtered by `organizationId`, for anything that doesn't match the pattern of that tenant's own known `OAuthClient`(s) and expected traffic volume.
- `event=login_success` / `event=login_failure` logs for the same `organizationId` around the suspected exposure window — a forged token doesn't require a real login, so a gap between login volume and token-issuance volume is itself a signal.
- Manual comparison of `/o/{organizationId}/oauth2/jwks`'s published `kid` against the `SigningKey` table row(s) for that Organization.

## 3. Immediate containment

**Corrected 2026-08-26** — the previous revision of this section said the containment path ADR-0010 §5.2 describes did not exist yet, and directed raw SQL against production plus a full restart. That was true when written (2026-08-21); it has not been true since **2026-08-23**, when TD-SEC-008 and TD-SEC-010 closed. This section sat un-updated for three days describing a procedure a real incident responder would have followed instead of the real, safer one that already existed — caught only because the user explicitly refused to accept "the code says it's done" without a live check (`technical-debt-register.md` TD-SEC-028's own 2026-08-25 entry), then asked the same question of this runbook directly. Treat a stale incident-response runbook as a live risk in its own right, not a documentation nicety — the whole point of this document is to be trustworthy *during* an incident, when there's no time to cross-check it against the code.

**The real containment path exists, is self-service, audited, and requires no direct database access:**

1. Confirm the compromise is real before acting (§1's trigger conditions) — rotation is cheap and safe, but still not something to trigger on a hunch; each rotation is a real, audited `signing_key.rotated` event (TD-SEC-007).
2. **Call the rotation endpoint**: `POST /api/v1/admin/organizations/{organizationId}/signing-keys/rotate`, authenticated with a platform-tier `client_credentials` token carrying the `platform:signing-keys:rotate` scope (same platform-tier-only, never-a-tenant's-own-token bar every other `/api/v1/admin/**` endpoint holds). No SQL, no restart, no process-wide blast radius. Response: `200` with the new `kid` (and the retired one, for the incident record), or `404` if the given `organizationId` has no active key at all (a bogus id, most likely, not a real containment case).
3. **Confirm eradication immediately, live, not by assuming the call succeeded**: `GET /o/{organizationId}/oauth2/jwks` and confirm the new `kid` is present. The *previously-compromised* `kid` will still be there too, deliberately — see the overlap tradeoff in step 5 below before treating that as unfinished.
4. **This has always been Organization-scoped, by construction, not by a restart's side effect** — `RotateSigningKeyForOrganizationService` only touches the one Organization named in the request; every other Organization's (and the platform tier's) own active key, session, and in-flight token are completely untouched. Nothing here requires a restart at all. **Exception, unchanged from before**: a compromise of the *platform* tier's own key has no equivalent self-service endpoint yet — there is still only one platform issuer, and forcing its rotation remains a manual, system-wide operation (this exception is real, current, and tracked below in §6, not new).
5. **Real overlap is a real tradeoff during an active compromise, not a pure win — understand it before treating rotation alone as containment complete.** JWKS keeps publishing the retired key for `clavaris.signing-key.jwks-overlap-hours` (default 24h, a fixed, app-wide config — not a per-incident lever; see TD-SEC-029) *specifically so legitimate tokens issued in the seconds before rotation don't break*. The same property that protects legitimate clients also means an attacker who still holds the compromised private key material can keep minting *new* forged tokens that verify successfully for the entire overlap window — rotation stops the compromised key from signing anything new *through this system*, but does not revoke trust in tokens *it* signs, for as long as JWKS keeps publishing it. If the compromise is confirmed severe (attacker demonstrably has usable private key material, not just "the `kid` looked wrong"), rotation alone is not full containment — proceed to step 6.
6. **No emergency, zero-overlap purge exists yet** (TD-SEC-029, tracked, open) — the only way to stop publishing the compromised key *before* the overlap window naturally elapses is the same direct-SQL lever this section used to recommend for the whole procedure: `UPDATE signing_keys SET retired_at = '<a timestamp older than the overlap window>' WHERE organization_id = '<id>' AND kid = '<compromised-kid>';` (this predates the row's real `retired_at`, which the rotation call in step 2 already set correctly — this step is a deliberate, logged, one-time backdating of that same value, not a correction of a bug). Confirm via step 3's own JWKS check that the compromised `kid` is now actually gone. Reserve this for a *confirmed* compromise, not routine rotation — it accepts breaking any legitimate token issued in the last few seconds before the original rotation, the exact cost overlap exists to avoid.
7. There is still no way to selectively invalidate only the compromised Organization's sessions/refresh tokens (TD-ARCH-002 closed 2026-08-23 — sessions are real, restart-surviving Redis state now, not in-process, but no per-Organization session-revocation endpoint exists on the tenant tier the way `PlatformAccountSessionRevoker` already does for the platform tier) — an active browser session established before rotation stays valid until it naturally expires or the account re-authenticates.

## 4. Investigation

- Pull every `event=token_issued`/`event=token_revoked` log line for the affected `organizationId` covering the full suspected exposure window (as far back as log retention allows — TD-TEST-002 flags that `event_outbox` has no retention policy yet, but this is application log retention, a separate, deployment-environment concern, not covered by that item).
- The token *value* is never logged (BR-DATA-01) — investigation can establish *volume and pattern* of issuance (grant type, client, principal, timing) but cannot directly confirm which specific historical tokens were forged versus legitimate. Treat any `client_id`/`principal` combination inconsistent with the tenant's own known `OAuthClient`(s) as the primary lead.
- Ask the affected consuming application to correlate their own access logs against the suspected window — they may have observed requests bearing a token this system's own logs show no matching issuance event for, which is itself evidence of forgery (a token verifying successfully but never actually issued by Clavaris).

## 5. Eradication and recovery

1. Complete §3 (rotate via the endpoint, and step 6's own backdated-`retired_at` purge if the compromise was confirmed severe enough to warrant it) if not already done.
2. Confirm eradication: fetch `/o/{organizationId}/oauth2/jwks` (or `/oauth2/jwks` for the platform tier) and confirm the new `kid` is present — and, if step 6's purge was used, that the previously-compromised `kid` is now actually gone, not just past its normal overlap window.
3. Determine and close the actual leak vector (credential scanning gap, log line that shouldn't exist, compromised host) before considering the incident closed — a repeat compromise of the *new* key via the same vector is a process failure, not a technology one.
4. Notify the affected tenant's own operator/engineering contact — scoped to the compromised Organization's own users, not every tenant's (§3.4), confirm with the affected consumer specifically rather than broadcasting a system-wide notice by habit.
5. No session was cleared by §3's own steps — rotation alone doesn't touch active `HttpSession`s (§3.7, TD-ARCH-002's own remaining gap). Decide explicitly whether the compromise's own severity warrants forcing every one of that Organization's active sessions to re-authenticate regardless (today, only achievable manually/at the infrastructure layer — no per-Organization session-revocation endpoint exists), and document that decision either way rather than assuming it happened as a side effect of containment.

## 6. Known limitations of this runbook, given the current implementation

This section exists so the gap between "what ADR-0010 §5 describes" and "what actually runs today" is never rediscovered mid-incident — that exact failure happened to an earlier revision of this section itself (2026-08-21 through 2026-08-25), which kept citing TD-SEC-003/008/010 as open three days after all three had actually closed. Re-verify every row here against `technical-debt-register.md` §2/§6 directly before trusting it mid-incident, don't trust this table's own age.

| Gap | What it means for this runbook | Tracked as |
|---|---|---|
| No self-service endpoint exists to force-rotate the *platform* tier's own key — only per-Organization rotation is self-service | A confirmed compromise of the platform tier's own signing key still has no lever short of a manual, system-wide operation | Not yet tracked as its own row — narrower restatement of the `PlatformClient`-compromise runbook's own, higher-severity scope; see `incident-response-platform-client-compromise.md` |
| No emergency, zero-overlap purge exists for a *confirmed* compromise — only the normal, deliberately-overlapping rotation, plus a manual `retired_at` backdate as the only way to force early eviction from JWKS (§3.6) | A responder has to know and execute the raw-SQL fallback themselves for the minority of compromises severe enough to warrant it; it isn't a first-class, audited operation the way rotation itself now is | **TD-SEC-029** |
| No per-Organization session-revocation endpoint exists (the platform tier has one, `PlatformAccountSessionRevoker` — the tenant tier doesn't) | An active browser session established before rotation stays valid regardless of containment — §3.7/§5.5 | TD-ARCH-002's own remaining scope (the persistence half of TD-ARCH-002 is closed; this is a distinct, narrower gap it left behind) |

Real, closed, and safe to rely on today, not listed as limitations: self-service Organization-scoped rotation with real cryptographic overlap (TD-SEC-008), audited via a real `signing_key.rotated` event (TD-SEC-007), persistent signing keys surviving a restart (TD-SEC-002), and persistent `OAuth2Authorization` state surviving a restart (TD-SEC-003) — all closed 2026-08-21–23, live-verified with cryptographic proof (`SigningKeyRotationIntegrationTest`), not merely configured. This runbook's own §3 above now reflects that reality directly rather than routing around it.
