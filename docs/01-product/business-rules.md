# Business Rules — Clavaris

🟡 En revisión

Rule IDs are referenced from code comments per this project's own commenting standard. Grouped by module.

## Identity (`BR-ID`)

- **BR-ID-01** — A password is never stored or logged in plaintext, anywhere, under any circumstance, including error logs and stack traces. Hashed with Argon2id (ADR-0005) before it touches persistence.
- **BR-ID-02** — An account may have multiple authentication methods (password, one or more social identities) simultaneously; removing one method requires at least one other to remain, so an account can never end up with zero ways to authenticate.
- **BR-ID-03** — Refresh tokens are single-use. Reuse of an already-rotated refresh token is treated as a compromise signal and revokes every active token for that account, not just the reused one.
- **BR-ID-04** — A password reset token is single-use, time-limited, and invalidates all of the account's active sessions and refresh tokens on successful reset — a password reset is treated as "assume prior sessions may be compromised," not just "change the credential."
- **BR-ID-05** — Email verification and password reset tokens are delivered only to the email address of record at time of request, never returned in an API response body — the token must not be observable by anything except the recipient's inbox.
- **BR-ID-06** — Rate limiting on login and token endpoints is mandatory from the first deployment, not added later once abuse is observed. Rate limiting must never throttle a legitimate token-refresh cycle for an already-active session — a documented failure mode in a comparable system (`clerk-feature-analysis.md` §7 item 2) that turned rate limiting into a self-inflicted outage. Since ADR-0010 §6, this is two layers, not one: a fixed, system-defined anti-abuse threshold per `(organization_id, account_or_ip_identifier)` that no tenant can loosen (the actual credential-stuffing defense), plus a separate per-`organization_id` capacity ceiling (tunable within a system-wide cap, operator-only in v1, BR-ORG-05) so one tenant's attack or traffic spike can never exhaust another tenant's budget.
- **BR-ID-07** — 🟡 v1.1, see `prd-mvp.md` §2.1. A password is checked against a breached-password corpus (k-anonymity range query, e.g. HIBP-style — the full password never leaves the server, only a truncated hash prefix) at registration and password-change time; a match is rejected with a generic "choose a different password" message, never revealing the source of the match.
- **BR-ID-08** — An `Account` can be reversibly suspended (banned) via the admin API, distinct from BR-DATA-02/03's permanent hard delete. Suspension revokes every live session/token immediately (same revocation ports the hard-delete path already uses) and blocks all future logins for that account until reactivated — enforced by the existing "reject any non-`ACTIVE` account" check in the login flow, not a separate gate. Reactivation reverses it; both transitions are audited.
- **BR-ID-09** — ADR-0020 Decision 1: a social login whose verified email matches an existing `Account` created by a different method (password, or a different `SocialProvider`) never links automatically. A pending link is created and requires explicit confirmation via the email address of record before the `SocialIdentity` row is attached — same delivery/consumption shape as `VerificationToken` (single-use, time-limited). Prevents an attacker who pre-registered an unverified email from silently intercepting the real owner's first social login.
- **BR-ID-10** — ADR-0020 Decision 2: `PlatformAccount` (Clavaris's own operator tier) supports both password and Google/GitHub social login, permanently and simultaneously — social login is additive, not a replacement; existing and new `PlatformAccount`s can use either method, same BR-ID-02 "multiple methods, never zero" shape already extended to this tier.
- **BR-ID-11** — Social login never renders inside an embedded surface — always a full-navigation redirect/popup, both for `Account` (tenant) and `PlatformAccount` sign-in. Same external constraint BR-CLIENT-05 already states for the OAuth consent screen (providers block iframe-embedded consent as an anti-clickjacking measure); restated here because this rule applies even outside the `OAuthClient`-embedded-login context BR-CLIENT-05 was originally scoped to (BR-CLIENT-05 covers a tenant's own `OAuthClient` login surface; this covers Clavaris's own hosted login pages, both tiers).
- **BR-ID-12** — ADR-0020 Decision 3: email/password sign-in for an `Organization`'s own `Account` population is always available and can never be disabled by any tenant setting. Whether social login is *additionally* offered, and with which providers, is a per-`Organization` opt-in setting (`social_login_enabled`, `allowed_social_providers`) — defaults closed (disabled, no providers). Never a per-`OAuthClient` setting.
- **BR-ID-13** (2026-08-31; extended to `PlatformAccount` 2026-09-02, TD-FUT-026) — Every tenant `Account` can self-service list and individually revoke its own live hosted-login sessions (`GET`/`POST /o/{organizationId}/account/sessions`). Listing/revocation is always scoped to the caller's own resolved `AccountId` from the authenticated session — never by a client-supplied identifier — so one Account can never see or revoke another's session, even by guessing a session id (`RevokeAccountSessionService`'s own ownership check). Mirrored, mechanically, for `PlatformAccount` (`GET`/`POST /platform/account/sessions`, `RevokePlatformAccountSessionService`) — same ownership-check shape, scoped by the caller's own resolved `PlatformAccountId` instead; no `organizationId` path segment at all, the platform tier has none.
- **BR-ID-14** (2026-08-31; extended to `PlatformAccount` 2026-09-02, TD-FUT-026) — A tenant `Account`'s first successful login from a device this system hasn't issued a `DeviceCookie` to before (TD-SEC-033: an opaque, `HttpOnly`, high-entropy cookie — not the raw `User-Agent` header, which is spoofable) triggers a "new sign-in" notification email to that Account's own address of record; a subsequent login presenting an already-recognized cookie sends nothing. A failed notification send never fails the login itself (deliberately different from every other transactional email in this system — see `RecordAccountLoginDeviceService`'s own Javadoc). v1 scope: informational only, no "this wasn't me" action link (TD-FUT-025, deliberately deferred). Mirrored, mechanically, for `PlatformAccount` (`PlatformDeviceCookie`, `RecordPlatformAccountLoginDeviceService`) — same cookie-based recognition, generic "Clavaris"-branded email (no Organization to brand with); deliberately does not publish an outbox/webhook event the way the tenant-tier version does, since no `Organization`-scoped `WebhookEndpoint` (ADR-0007) can ever be relevant to `PlatformAccount` activity.
- **BR-ID-15** — ✅ shipped 2026-09-04 (Clerk Development/Production instances analysis, BR-ORG-08). Requesting email verification or password reset for an `Account` under a `DEVELOPMENT`-environment `Organization` never triggers a real outbound send — the `VerificationToken` itself is still genuinely created and completable exactly as normal, only the network call to the mail provider is skipped, logged as a structured, PII-free `event=..._bypassed_development_environment` line. **Named limitation, not silently solved**: this alone does not give an out-of-process caller (a human tester, an external e2e suite) a way to retrieve the raw token — a real "read it back without a real inbox" channel is separate, larger, deliberately deferred work.
- **BR-ID-16** — ADR-0024 Decision 1. Every per-`Organization` sign-up/sign-in policy choice (email verification method, passwordless email sign-in, username, optional password, device trust) lives on `AccountAuthenticationPolicy`, one row per Organization; absence of a row means the exact pre-ADR-0024 defaults, not an error. Email/password sign-up and sign-in are never fields on this policy — both stay permanently available for every Organization, the same fixed posture BR-ID-12 already established for password before this rule existed.
- **BR-ID-17** — ADR-0024 Decision 2/3. `emailVerificationRequiredAtSignIn=true` rejects a sign-in whose `Account.emailVerifiedAt()` is empty, checked only after the primary factor (password, username, or a passwordless email proof) has already succeeded — never before, so the rejection can never itself be used to probe which accounts exist. A passwordless email sign-in (`authenticatewithemailcode`/`authenticatewithemaillink`) marks the email verified as a side effect of that same successful proof rather than being blocked by this gate — an Organization whose only enabled sign-in method is itself the passwordless one can never lock every one of its own accounts out.
- **BR-ID-18** — ADR-0024 Decision 3. A 6-digit one-time code (email sign-in code, device-trust challenge) is capped at 5 failed presentation attempts per issued token, enforced at the HTTP layer via the existing rate-limiting filter, keyed by the submitted email/account field — a 6th attempt is rejected regardless of correctness, requiring a fresh request. Does not apply to the 256-bit magic-link token (BR-ID-05's own "not observable outside the recipient's inbox" property already makes brute force infeasible for that shape).
- **BR-ID-19** — ADR-0024 Decision 2. Password-optional sign-up (`passwordAtSignUpEnabled=false`) never creates an `Account` with zero authentication methods, even transiently: when no password is submitted, a cryptographically random, never-surfaced password credential is attached instead of skipping credential attachment — the account's real first sign-in always happens through the passwordless email flow this same policy state requires be enabled (`SetAccountAuthenticationPolicyForOrganizationService`'s own validation, BR-ID-16), never through the generated value.
- **BR-ID-20** — ADR-0024 Decision 4. `Username` uniqueness is scoped `(organization_id, username)`, the same tenant-isolation shape every other per-Organization uniqueness constraint in this system already uses (ADR-0010) — two Organizations may have accounts sharing the identical username with no conflict, since usernames from one Organization's account pool are never visible or resolvable from another's.
- **BR-ID-21** — ADR-0024 Decision 5. `deviceTrustEnabled=true` pauses a sign-in from a device this system has not previously recognized for that exact `Account` (the same `KnownDevice`/`DeviceCookie` recognition primitive TD-SEC-033/BR-ID-14 already established) behind a step-up one-time-code challenge (BR-ID-18's brute-force cap applies) before the session is established — never after. A device recognized before the policy was enabled for that Organization stays recognized; this rule only ever challenges a genuinely new device going forward, a named limitation, not a retroactive re-challenge of already-trusted devices.

## Organizations — tenant isolation (`BR-ORG`) — 🟡 see ADR-0010

- **BR-ORG-01** — Every `Account` belongs to exactly one `Organization`; there is no cross-organization identity — the same email address may exist as entirely independent `Account` rows in different organizations, with no linkage, shared session, or shared credential between them.
- **BR-ORG-02** — Every `OAuthClient` belongs to exactly one `Organization`. The hosted login page for a given `client_id` only ever authenticates against that client's own `Organization`'s account pool — a login screen never has a code path capable of seeing or authenticating an `Account` from a different `Organization`.
- **BR-ORG-03** — Gaining access to a second `Organization` requires a separate, explicit registration in that organization — never an invitation, membership grant, or any mechanism that reuses an existing `Account` across organizations.
- **BR-ORG-04** — Every `Organization` has its own RS256 signing key pair, its own issuer (`{clavarisBaseUrl}/o/{organizationId}`, path-based per ADR-0010 §5.1), and its own JWKS document; a token issued under one Organization's key is never verifiable against another Organization's JWKS. Key rotation with overlap runs independently per Organization; v1 rotation is a manually-triggered, audited management-API operation, not a scheduled job (ADR-0010 §5.2).
- **BR-ORG-05** — Rate limiting on login/token endpoints is enforced in two layers per Organization (ADR-0010 §6): a fixed, system-defined anti-abuse layer keyed by `(organization_id, account_or_ip_identifier)` that is **never** tenant-configurable (BR-ID-06), and a per-`organization_id` aggregate capacity ceiling that an Organization may tune within a hard system-wide cap. In v1, only the capacity ceiling exists as a configurable `RateLimitPolicy`, and only a Clavaris operator can set it — tenant self-service is deferred to v1.1, gated on audit logging of every change.
- **BR-ORG-06** — `Organization` creation happens either via a Clavaris operator (`POST /api/v1/admin/organizations`, `PlatformClient`-authenticated) or, since ADR-0012, via the owning `PlatformAccount` itself through the session-authenticated dashboard — either path resolves to the same `CreateOrganizationUseCase`, and either way its initial `SigningKey` is generated and activated synchronously, in the same operation — an `Organization` that exists but cannot yet issue a token is never an observable state. **Updated 2026-09-04** (Clerk Development/Production instances analysis): every new Organization defaults to `DEVELOPMENT` environment (BR-ORG-08) — a real, explicit, low-default `RateLimitPolicy` row is provisioned for it at this step, unlike a `PRODUCTION` Organization, which still gets none (BR-ORG-05's system default still covers that case, unchanged). Registering the Organization's first real `OAuthClient` is a separate, subsequent action, not bundled into provisioning.
- **BR-ORG-07** — ADR-0012: every `Organization` has exactly one owning `PlatformAccount` (`organizations.owner_platform_account_id`); a `PlatformAccount` may own many Organizations. No multi-owner/membership model in v1 — not to be confused with `Workspace` membership (`BR-WS`), which is a different concept at a different tier entirely.
- **BR-ORG-08** — ✅ shipped 2026-09-04 (Clerk Development/Production instances analysis). Every `Organization` has an `environment` (`DEVELOPMENT` or `PRODUCTION`) — a policy distinction, never a different isolation model: a `DEVELOPMENT` Organization gets exactly the same structural isolation (its own issuer, JWKS, account pool, ADR-0010 §5) any other Organization gets. `POST /api/v1/admin/organizations` always creates `DEVELOPMENT` going forward (the safer default); every Organization that existed before this rule shipped defaults to `PRODUCTION`, unchanged. `POST /api/v1/admin/organizations/{id}:create-production-environment` promotes a `DEVELOPMENT` Organization by creating its paired `PRODUCTION` sibling (a new, separate `Organization` row, linked both ways via `linked_environment_organization_id`) — only ever from `DEVELOPMENT`, and only once per Organization (an already-linked Organization cannot be promoted again). No data — no `Account`, no `OAuthClient` — is ever copied between the two; an operator registers new clients under the `PRODUCTION` Organization the same way as for any other. Two concrete policy differences apply to a `DEVELOPMENT` Organization: (1) a real, explicit, low-default `RateLimitPolicy` (BR-ORG-06); (2) `OAuthClient.client_id` is prefixed `test_` instead of `live_` at registration (same "the credential itself tells you which environment it belongs to" mechanic as a `pk_test_`/`pk_live_` key). BR-ID-15 covers the third: verification email/password-reset bypass.
- **BR-ORG-09** — ✅ shipped 2026-09-05 (ADR-0022, amending ADR-0020 Decision 4). A `PRODUCTION` Organization may bring its own Google/GitHub OAuth app credentials (`PUT /api/v1/admin/organizations/{id}/social-credentials/{provider}`), used in place of Clavaris's own shared app for that provider's login flow — additive on top of ADR-0020 Decision 3's own `social_login_enabled`/`allowed_social_providers` gate, never a bypass of it (setting credentials for a provider the Organization hasn't allowed is rejected). Never available to a `DEVELOPMENT` Organization or the platform tier — always the shared app there, no exceptions. `client_secret` is encrypted at rest (AES-256-GCM, `SOCIAL_CREDENTIAL_ENCRYPTION_KEY`) and never round-trips back out of the system in any form once written, not even to the operator who set it. Per-provider independent — an Organization may bring its own Google credentials while still using the shared GitHub app. Does not, and structurally cannot, rebrand Clavaris's own hosted login/consent page — that is ADR-0009's own separate concern; this rule only changes which app's consent screen Google/GitHub themselves show.

## Platform tier (`BR-PLATFORM`) — see ADR-0010, Organization provisioning

- **BR-PLATFORM-01** — Operations that create or manage `Organization` rows themselves (including `Organization` creation) can never be authenticated by a token that belongs to an `Organization` — doing so would let a compromised tenant client reach across the isolation boundary BR-ORG-01–03 exist to establish. These operations are authenticated exclusively via a `PlatformClient`, issued a token by a dedicated platform issuer structurally separate from every tenant's own OIDC surface (never `/o/{organizationId}/...`).
- **BR-PLATFORM-02** — The entire `/api/v1/admin/*` management-API surface accepts platform-tier tokens only in v1 — no `OAuthClient` belonging to any `Organization` may call it, not even to manage its own `Organization`. Tenant self-service is v1.1+ scope, already deferred for other reasons (self-service client console, self-service `RateLimitPolicy`); this is the same deferral applied consistently, not a new exception.
- **BR-PLATFORM-03** — The first `PlatformClient` is provisioned from deployment-environment configuration (`PLATFORM_BOOTSTRAP_CLIENT_ID`/`PLATFORM_BOOTSTRAP_CLIENT_SECRET`) via an idempotent startup check, never via an HTTP endpoint and never via a credential shipped in code — it is the one trust root in the system that cannot derive from anything else already inside it.
- **BR-PLATFORM-04** — ✅ shipped 2026-09-05 (ADR-0023, Clerk "Secret Key" parity). `BR-PLATFORM-02`'s own rule is amended with one deliberate exception: an `OrganizationClient` (a `client_credentials` credential scoped to exactly one `Organization`, minted only by a `PlatformClient` — no self-service issuance) may reach a fixed, explicitly-named allowlist of `/api/v1/admin/**` endpoints, enforced by `OrganizationClientOwnershipFilter` matching the token's own `organization_id` claim against the request's resolved target Organization — any endpoint not on that allowlist, or a resolved Organization that doesn't match the claim, is a `403`, fail-closed by construction, never a silent pass-through. `PlatformClient` tokens (no `organization_id` claim) are completely unaffected — this rule adds a narrower, second credential tier, it does not loosen the platform tier's own unscoped reach. `allowedScopes` reuses `PlatformScopes`' own string constants verbatim, not a parallel scope namespace — the same use cases, narrowed by which Organization they may target, not by which actions exist.
- **BR-PLATFORM-04** — ADR-0012: `PlatformAccount` (a human, self-service identity, distinct from `PlatformClient`) authenticates via a plain session-authenticated login (`/platform/login`), never an OAuth token — no `OAuth2AuthorizationService`/`RegisteredClient` involvement, and never confusable with the platform tier's own `client_credentials` issuer (`{clavarisBaseUrl}/oauth2/...`).
- **BR-PLATFORM-05** — ADR-0012: a `PlatformAccount` password reset revokes every active session for that account (BR-ID-04's equivalent at this tier), enforced via Spring Security's `SessionRegistry`/`ConcurrentSessionFilter`, not a custom refresh-token cascade — there is no `PlatformRefreshToken`/`PlatformSession` domain concept, deliberately (ADR-0012's own "no OAuth token issuance" decision).

## Workspaces (`BR-WS`) — renamed from the pre-ADR-0010 `BR-ORG` rules; a Workspace is a team/company grouping *inside* one Organization's account pool, not the tenant boundary itself

**v1 scope note (ADR-0010 §3 addendum, 2026-08-27):** BR-WS-01 and BR-WS-02 below are rewritten from
their original design (`OWNER`/`ADMIN`/`MEMBER` + invitations) to match an explicit, deliberate v1
scope decision — see the addendum for the full rationale. The renumbering keeps `BR-WS-03`'s ID
stable since its substance (immediate revocation on removal) is unchanged, only clarified.

- **BR-WS-01** — A workspace must always retain at least one `ADMIN` member; a role change or
  removal that would leave zero `ADMIN`s is rejected. Enforced at the application layer, not left to
  a database constraint alone. Replaces the original `OWNER`-with-atomic-transfer design — v1 has no
  `OWNER` role, only `ADMIN`/`MEMBER` (BR-WS-05).
- **BR-WS-02 (deferred to v1.1+)** — An invite-by-email-then-accept flow is not built in v1; see
  BR-WS-04 for the v1 mechanism (direct provisioning). Kept as a placeholder ID so a future
  `WorkspaceInvitation` doesn't have to renumber anything else in this section.
- **BR-WS-03** — Removing a member revokes that member's access to the workspace's resources
  immediately, **stated honestly for v1**: there is no workspace-scoped token/authorization concept
  in Clavaris yet (tokens are Account/OAuthClient-scoped per Organization, not per-Workspace) — in
  v1, "immediate" means the admin-API listing and the corresponding outbox event fire synchronously
  with the removal, not that a live token is invalidated (none exists to invalidate). A consuming
  application that gates its own authorization by workspace membership must re-check membership
  itself, or subscribe to the corresponding webhook event (`workspace_membership.removed`/
  `.role_changed`, now real — `webhook-module`, ADR-0007, shipped 2026-09-02) — see
  `api-contract-overview.md` §6 (TD-WS-002) for the full, concrete integration guidance.
- **BR-WS-04** — A workspace member is provisioned directly: adding a member creates a real
  `Account` (identity-module) scoped to the workspace's own Organization and immediately triggers
  that Organization's existing password-reset-request flow, so the new member sets their own
  password on first login. There is no invitation-accept step in v1 (see BR-WS-02).
- **BR-WS-05** — Workspace roles are Clavaris-internal only: `ADMIN` (can manage the workspace's own
  membership) or `MEMBER` (cannot) — nothing else. Any business/product-domain role (e.g.
  "recruiter", "candidate") is explicitly out of scope here; that differentiation belongs entirely to
  the consuming application (e.g. JobSeeker), never to Clavaris.
- **BR-WS-06** — A member's current `workspace_id`/`workspace_role` are carried as claims on every
  ID token and access token the interactive Authorization Code flow issues for that Account, and on
  the corresponding `/userinfo` response — the mechanism a consuming application uses to know, at
  login time, whether that user should see its own admin surface. Refreshed on every login and on
  every silent token refresh (both reissue through the same token-generation path); there is no
  separate polling or webhook step required to observe a role change for an account that's about to
  authenticate again. Omitted entirely (not a null/empty claim) for an Account with no Workspace
  membership.

## Client registry (`BR-CLIENT`)

- **BR-CLIENT-01** — A registered client's `redirect_uris` are an exact-match allowlist; no wildcard or partial matching, to close the standard OAuth2 open-redirect attack class.
- **BR-CLIENT-02** — A token issued for one `client_id` is never valid against another client's resources without an explicit, separately-designed cross-client mechanism (not present in v1). Since ADR-0010, this is additionally structural whenever the two clients belong to different `Organization`s: the token's `Account` doesn't exist outside its own `Organization`, so cross-organization validity isn't just disallowed, it's meaningless.
- **BR-CLIENT-03** — The Authorization Code flow requires PKCE for every client, including confidential clients — defense in depth, not just a public-client requirement, since it costs nothing and closes an entire attack class outright.
- **BR-CLIENT-04** — 🟡 v1.1/v2, see ADR-0009. A production `OAuthClient` using the embedded iframe-modal login experience must have a verified custom domain (`CNAME` or `PROXY` mode) — `SHARED` mode (Clavaris's own domain) is development-only, because third-party cookie blocking makes the embedded experience silently degrade in production without a clear failure signal.
- **BR-CLIENT-05** — 🟡 v1.1/v2, see ADR-0009. Social login (Google, GitHub, etc.) never renders inside the embedded iframe — it always opens as a full-navigation popup window. This is a hard external constraint (providers block iframe-embedded consent screens as an anti-clickjacking measure), not a design choice Clavaris can relax.

## Data protection and account deletion (`BR-DATA`)

- **BR-DATA-01** — No PII (passwords, tokens, email addresses in bulk) appears in application logs, ever — mirrors JobSeeker's own BR-DATA-01, restated here because it's independently enforced in this codebase, not inherited.
- **BR-DATA-02** — Clavaris exposes an authenticated admin API endpoint for account deletion, used by consuming applications (e.g. JobSeeker, per its own ADR-0013) to trigger identity deletion once their own local anonymization/grace-period process completes. Clavaris does not run its own independent grace period — the consumer owns that decision; Clavaris deletes on request.
- **BR-DATA-03** — Deleting an account via the admin API cascades: all sessions and refresh tokens are revoked immediately, all workspace memberships are removed, and the account's own record is hard-deleted (not anonymized) — see the flagged caveat in JobSeeker's ADR-0013.
- **BR-DATA-04** — Social identity links are deleted alongside the account; no orphaned linkage rows survive account deletion.

### Open question flagged by this rule set — resolved by ADR-0010

BR-DATA-02/03 previously flagged an open question: what happens if the *same person* has one Clavaris account used to log into two different consumers, and a deletion request from one consumer's data-deletion flow shouldn't silently delete an identity the other consumer depends on. ADR-0010 resolves this by construction — `Account` is scoped to exactly one `Organization` (one consuming system), so there is no scenario where one `Account` row is shared across two consumers in the first place. A deletion request against one `Organization`'s account can never affect another `Organization`.

## Admin support tooling (`BR-ADMIN`) — ✅ shipped 2026-09-03 (Impersonation only — see `clerk-feature-analysis.md` §6 for the rest of this section's original v1.1 scope)

- **BR-ADMIN-01** — User impersonation (an operator signing in *as* an account to debug a reported issue) requires its own elevated management-API scope (`platform:accounts:impersonate`), is audited as its own distinct event (`account.impersonation_started`, actor + target `Account` id — `ImpersonateAccountService`), and expires after a short, fixed lifetime. **Implementation note**: the shipped design uses a short, fixed access-token TTL (the same default every `OAuthClient` access token already gets, ~5 minutes) rather than a sliding inactivity window — this rule's original "inactivity timeout" phrasing described the intent (an impersonation grant must not silently outlive the operator's actual need for it) more precisely than the exact mechanism; a minted access token has no notion of "activity" to slide against once issued, and a short fixed TTL achieves the same bound more simply. No refresh token is issued, so the grant cannot be silently extended.
- **BR-ADMIN-02** — An impersonation session is never indistinguishable from the real account's own session to anything downstream: every token issued during impersonation carries an RFC 8693 `act` claim (`{"sub": <operator's PlatformClient id>, "type": "PLATFORM_CLIENT"}`) plus `amr: ["imp"]`, so a consuming application can choose to restrict what an impersonated session is allowed to do (e.g. block payment actions) — never silently invisible. Implemented in `ImpersonationTokenIssuer` (`app`); revocable via the same `/oauth2/revoke` every other token this system issues already is.

## Webhooks (`BR-WEBHOOK`) — ✅ shipped 2026-09-02, `webhook-module` (ADR-0007)

- **BR-WEBHOOK-01** — Every webhook payload is signed HMAC-SHA256 with the receiving endpoint's own secret (`Clavaris-Signature` header, timestamp + signature); a consumer that does not verify this signature is trusting an unauthenticated HTTP request, so the signing step is never optional or skippable per-endpoint. During a secret rotation's overlap window, a delivery carries one `v1=` signature per still-valid secret (current and previous), never just one, so a consumer verifying against either is never wrongly rejected mid-rotation.
- **BR-WEBHOOK-02** — Delivery is at-least-once, never at-most-once. Every event carries a stable `event.id` (`Clavaris-Event-Id` header — the source outbox row's own id); consumers are responsible for deduplicating on it. Clavaris does not promise exactly-once delivery — that promise cannot be made honestly over plain HTTP with retries.
- **BR-WEBHOOK-03** — A failed delivery (non-2xx response or timeout) retries with exponential backoff and jitter up to a fixed attempt limit (default 8); after the final attempt it is marked `EXHAUSTED`, never silently dropped, and stays visible for manual replay via the management API (`POST .../deliveries/{id}:replay`).
- **BR-WEBHOOK-04** — Clavaris never writes directly to a consumer's database, filesystem, or infrastructure. The only integration surfaces are the signed webhook payload and the standard OIDC/management APIs — preserves the "any language, no special access" reusability goal (ADR-0001, ADR-0006).
- **BR-WEBHOOK-05** — The outbox row for a domain event is written in the same database transaction as the state change that produced it (ADR-0007 §1) — an event is never observably lost because the process crashed between "state committed" and "event published."
- **BR-WEBHOOK-06** — A `WebhookEndpoint` is only ever sent an event type it explicitly subscribed to at registration; an endpoint registered for `account.created` never receives `account.deleted`.
- **BR-WEBHOOK-07** — A `WebhookEndpoint`'s own URL must use `https`; a plain-`http` registration is rejected outright. Signing proves authenticity and integrity, not confidentiality — a plain-http delivery would still expose the payload in transit to any network observer.
