# ADR-0014: Infisical (self-hosted) for secrets management, not HashiCorp Vault or a custom build

**Status:** ✅ Aprobado (2026-08-24)

## Context

`technical-debt-register.md` TD-FUT-014 (SDE-III review, 2026-08-24) named a real, previously-unnamed gap: every production secret this project has (`TOKEN_SIGNING_KEY_STORE_PASSWORD`, `OAUTH2_TOKEN_HASH_SECRET`, `PLATFORM_BOOTSTRAP_CLIENT_ID`/`SECRET`, `DB_DEV_PASSWORD`, `RESEND_API_KEY`) is delivered only via plaintext `.env`/process environment variables — correctly gated by `docker-compose.yml`'s own hard `${VAR:?...}` pattern (TD-SEC-013's precedent) so nothing silently defaults, but with no secrets-manager story behind any of it. Acceptable for a solo-developer, pre-launch, own-laptop-only phase; a real gap the moment a second operator, a shared host, or any real deployment exists.

Three real options exist, evaluated on their own merits before deciding:

- **HashiCorp Vault** — the industry-standard secrets manager: dynamic (short-lived, auto-rotated) database credentials, a fine-grained HCL policy engine, official Spring Cloud Vault integration, and the name a future external security reviewer (`CLAUDE.md` §6, non-negotiable before launch) already trusts on sight. Against that: real operational burden disproportionate to a solo developer — its own unsealing process (or a cloud KMS dependency for auto-unseal, ironic given no cloud provider is chosen yet), its own storage-backend HA/backup design (the same class of problem TD-FUT-006 already names for Postgres, now duplicated for Vault itself), and it becomes a second asset of `PlatformClient`-bootstrap-credential severity (`CLAUDE.md` §5) with no incident-response runbook, same real gap that credential already has. HashiCorp also relicensed Vault from MPL to BUSL in 2023 — no longer open source in the strict sense; **OpenBao** (the Linux Foundation's post-relicense fork) is the closer match to this project's own "full ownership" reasoning (ADR-0001) if license purity matters, but is younger still than Vault itself.
- **Infisical (self-hosted)** — purpose-built for exactly this profile: a small team/solo developer wanting real secret storage, versioning, and access control without Vault's operational weight. Self-hosts as one more Docker Compose service, backed by Postgres (a database this project already operates), with a CLI (`infisical run --`) that injects secrets as plain process env vars — meaning **zero Spring/Java code change** is needed, since every secret this project reads already comes in through `${VAR:default}` placeholders. Against that: no dynamic-secrets engine (static secrets with versioning/access-control/audit, not full lifecycle management like Vault's database/cloud-IAM engines), a smaller community/track record than Vault, and — same relicensing risk class as Vault itself — a venture-funded open-source company behind it.
- **Build one from scratch.** Rejected on the same grounds ADR-0001 already ruled out hand-rolling the OAuth2/OIDC state machine: *"this does not mean reinventing cryptography... 'built from scratch' means owning the product, not hand-rolling security primitives."* A secrets manager — envelope encryption, key derivation, access control, audit logging, rotation — is squarely a security primitive, not "the product" (accounts/organizations/OAuth clients). It would also directly inflate the cost of the mandatory external security review (`CLAUDE.md` §6): instead of "we use a named, community-vetted tool, here's our configuration," a reviewer would have to audit a from-scratch crypto/access-control system with exactly one prior set of eyes on it. The actual problem in scope — delivering ~9 named secrets to one process — doesn't need a general-purpose secrets *platform* built to solve it; that's the same over-building this project's own YAGNI convention already rules out elsewhere (`common` module, TD-ARCH-001's own precedent).

## Decision

**Self-hosted Infisical**, not Vault and not a custom build. Rolled out as **Phase 2** of a two-phase plan (Phase 1, already usable today with zero code: a SOPS+age-encrypted `.env`, doc-only, no service to run):

- Three new Docker Compose services (`infisical-db`, `infisical-redis`, `infisical`), in a **separate** compose file (`docker-compose.infisical.yml`), not a `profiles:` block inside `docker-compose.yml` itself — a real bug caught live while implementing this: Compose evaluates every `${VAR:?...}` required-variable check for every service in a file regardless of whether that service's own profile is active, so the first attempt at a `profiles: ["infisical"]` approach broke the plain `docker compose up` flow outright on Infisical's own unset bootstrap secrets. A file never passed via `-f` is never parsed at all, which is what actually keeps the default local-dev flow completely unchanged. Deliberately separate `infisical-db`/`infisical-redis` instances, not shared with Clavaris's own `postgres`/`redis` — the same tenant-isolation-by-construction reasoning ADR-0010 applies to every `Organization`'s own data extends to keeping Infisical's own blast radius structurally apart from Clavaris's.
- `app/docker-entrypoint.sh`, a new dual-mode entrypoint: if `INFISICAL_CLIENT_ID`/`INFISICAL_CLIENT_SECRET` are set, it authenticates via Universal Auth (a machine identity, not a long-lived static token) and execs the app through `infisical run`, which injects every real secret as a process env var before the JVM ever starts; otherwise it falls back to today's behavior (`java -jar app.jar` reading the plaintext vars `docker-compose.yml` already provides) unchanged. This is a deliberate migration path, not a hard cutover — Infisical's own one-time bootstrap (first admin account, project, machine identity — `infisical-setup.md`) requires a human in its web UI, something nothing in this repository's tooling can complete unattended.
- The Infisical CLI is installed in the runtime image at a pinned exact version (`0.43.125`, confirmed live by actually running the real install sequence in a real `eclipse-temurin:25-jre` container before pinning it, not copied from documentation alone) — same "no silently-drifting tool version" discipline TD-ARCH-006 already established for the Maven Wrapper.

## Consequences

- **Positive:** the ~9 secrets this project already has move from "plaintext in a `.env` file with no access control or audit trail" to a real store with versioning, per-identity access control, and an audit log — without a single line of Spring/Java code changing, since Infisical delivers secrets as the same env vars this project already reads.
- **Positive:** operationally proportionate to a solo developer today — one more Compose service backed by Postgres, not a system that itself needs an incident-response runbook the way Vault's own unsealing/HA story would demand.
- **Positive:** the dual-mode entrypoint means this ADR carries zero risk to the existing, working local-dev flow — nothing breaks for a developer who never runs the `infisical` profile at all.
- **Negative:** Infisical is less battle-tested than Vault and offers no dynamic-secrets engine — if a future requirement genuinely needs short-lived, auto-rotated database credentials (not just versioned static secrets), this decision will need revisiting, not extending.
- **Negative:** like Vault, Infisical is a venture-funded open-source company's product — a future relicensing or commercial pivot is a real, if not currently acute, risk worth re-checking before this ADR is treated as permanently settled.
- **Negative:** this is now a locked decision per `CLAUDE.md` §10's convention — revisiting it (e.g. migrating to Vault/OpenBao once real operational maturity exists, `CLAUDE.md` §3's own "modular monolith initially... revisit only if" pattern) requires an explicit new ADR, not a quiet swap.

## Alternatives considered

See "Context" above — HashiCorp Vault/OpenBao and a from-scratch build were both evaluated in full before this decision, not assumed away.
