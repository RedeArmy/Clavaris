# ADR-0016: Build toward ISO/IEC 27001 + SOC 2 Type II readiness now; defer the paid, formal certification audit; adopt ISO/IEC 29115 immediately

**Status:** ✅ Aprobado (2026-08-24)

## Context

A direct request to pursue ISO certification for this project, since login/identity is exactly the kind of surface such a certification is meant to give confidence about. Investigated live before deciding, not assumed:

- **Cost/timeline (verified live, 2026 figures):** ISO/IEC 27001:2022 certification runs **$25,000–$40,000 in the first year** for a small organization, **200–800+ internal hours** over **6–12 months** minimum, plus recurring surveillance-audit costs every year after. This is for a funded startup *with a team* — disproportionate for a solo-developer, pre-launch project with zero real users.
- **What ISO 27001 actually certifies:** an organization's Information Security Management System (ISMS) — documented risk assessment, a Statement of Applicability mapping Annex A's 93 controls, management review cycles, and *evidence the system has operated this way for months*, verified by an accredited external certification body across two audit stages. It is not a code audit, and it cannot be "refactored into" — most of the work is organizational process and governance, only partly technical control implementation.
- **Market precedent (verified live, not assumed):** the two identity-provider companies most comparable to this project's own long-term ambitions — Clerk (this project's own explicitly stated model to eventually resemble) and Auth0 (larger, enterprise-focused) — take different paths. **Clerk holds SOC 2 Type II, not ISO 27001** — its own infrastructure runs on already-ISO-27001-certified providers (Google Cloud, Cloudflare) rather than Clerk pursuing its own certification. **Auth0 holds both**, but Auth0 is a mature company with a dedicated compliance team, not a useful comparison point for this project's current stage. The realistic precedent for where this project actually is today is Clerk's: SOC 2 Type II is the market-expected signal, not ISO 27001, and even Clerk didn't pursue it at solo-founder, pre-launch scale.
- **ISO/IEC 29115** (Entity Authentication Assurance Framework) is a different kind of standard entirely — not an organizational certification, a *protocol-level* framework OpenID Connect Core itself already references for interpreting the `acr` claim (its own §3.1.3.7: "the value '0' indicates the End-User authentication did not meet the requirements of ISO/IEC 29115 level 1"). Adopting it means representing authentication strength correctly in issued tokens, a real code change with a small, bounded scope — not a certification to schedule and pay for.
- **A genuine gap found while investigating this**, not assumed: `security-architecture.md` §7 described the admin account-deletion API (BR-DATA-02) as though it were implemented. It has zero code — the same "documented control that doesn't actually exist" pattern an external auditor (ISO, SOC 2, or the mandatory security review, `security-architecture.md` §9) would flag immediately. Corrected in the same pass as this ADR — see `technical-debt-register.md` TD-PROC-006.

## Decision

Three separate tracks, not one undifferentiated "get compliant" effort:

1. **ISO/IEC 27001-readiness and SOC 2 Type II-readiness, in parallel, without paying for either audit yet.** The two frameworks overlap heavily (ISO Annex A's control themes and SOC 2's Common Criteria cover mostly the same ground: access control, change management, monitoring, incident response, risk management, vendor management), so building toward both at once is not double work. "Readiness" here means concretely: closing genuine, verifiable control gaps this project already has the documentation infrastructure to track (`technical-debt-register.md`, `threat-model-stride.md`, `security-architecture.md`) — not producing paperwork for its own sake. New gaps found during this pass are tracked as real rows, not fabricated to look thorough (see `technical-debt-register.md` for the specific new items this ADR creates).
2. **ISO/IEC 29115 adopted immediately, as code, not deferred.** Every ID token the interactive Authorization Code flow issues now carries `acr`/`amr` claims (`AuthenticationContextClaimsCustomizer`, wired into `OrganizationAuthorizationServerConfig`). Today Clavaris has exactly one authentication method (`AuthenticateWithPasswordUseCase`, single-factor, BR-ID-02) — ISO/IEC 29115's own four-level framework places single-factor knowledge-based authentication at **Level 2** ("some confidence"), so every token gets `acr=urn:clavaris:loa:2`, `amr=["pwd"]`. The URN is minted by this project itself, not registry-assigned — ISO/IEC 29115 defines the levels, not a canonical URN per level; Open Banking Brazil's own security profile (`urn:brasil:openbanking:loa2`/`loa3`, confirmed live against its published spec) is the real, followed precedent for this pattern, not an invented one.
3. **The formal, paid certification audit for either ISO 27001 or SOC 2 is explicitly deferred**, not abandoned — the trigger is a real enterprise customer's procurement process requiring it, the same way most startups actually end up certifying, not a proactive milestone on this project's own timeline. Revisiting this trigger condition (i.e., certifying earlier than that) requires an explicit new ADR, not a quiet change of plan.

## Consequences

- **Positive:** ISO/IEC 29115 adoption is real today, not aspirational — verified end-to-end (a real signed ID token from a live Authorization Code exchange carries the claims, not just a unit-tested customizer in isolation).
- **Positive:** the readiness work has a real, immediate side benefit independent of ever certifying: it surfaced a genuine documentation-accuracy bug (`security-architecture.md` §7) that the mandatory external security review (`security-architecture.md` §9) would otherwise have found first, at worse cost.
- **Positive:** zero premature spend — the $25k–$40k first-year cost this ADR's own research found stays avoided until a real customer justifies it, consistent with this project's own "don't build ahead of the use case" discipline applied elsewhere (`common`/TD-ARCH-001, `OrganizationCapacityRateLimitingFilter`'s deliberately uncached policy lookup).
- **Negative:** "readiness" without certification carries no externally-verifiable proof — a prospective enterprise customer asking "are you SOC 2 certified?" still gets "not yet," not a certificate, regardless of how much control work has actually shipped. This is the accepted tradeoff, not an oversight.
- **Negative:** like every ADR, revisiting the deferral trigger (i.e., choosing to certify proactively rather than customer-driven) requires an explicit new ADR, not a quiet change of plan.

## Alternatives considered

- **Pursue full ISO 27001 certification now.** Rejected — see Context: cost/timeline is disproportionate to this project's actual stage, and it doesn't match how even mature, well-funded comparables (Clerk) approached the same decision at a similar point in their own life.
- **Do nothing until a customer asks.** Rejected — the readiness work has real value independent of certification (it already found a genuine documentation-accuracy gap in this pass alone), and ISO/IEC 29115 specifically has essentially zero cost to adopt now versus real design debt if deferred until a second authentication method (MFA, social login) makes retrofitting `acr`/`amr` semantics harder to get right.
- **Adopt a made-up or borrowed `acr` URN scheme** instead of minting Clavaris's own. Rejected — ISO/IEC 29115 doesn't publish one, and using a scheme registered to a different ecosystem (e.g., literally reusing Open Banking Brazil's own URNs) would misrepresent what those specific values mean; minting a clearly-namespaced one (`urn:clavaris:loa:2`) while following the same real-world pattern is the honest middle ground.
