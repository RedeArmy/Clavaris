# ADR-0017: Per-client, secure-by-default authorization consent

**Status:** ✅ Aprobado (2026-08-25)

## Context

`technical-debt-register.md` TD-SEC-026 (SDE-III review, 2026-08-24, surfaced while implementing TD-SEC-009's CSP for the hosted login/consent UI) found a real, previously-undocumented gap: `OrganizationRegisteredClientRepository.toRegisteredClient(...)` builds `ClientSettings.builder().requireProofKey(true).build()` and nothing else, so Spring Authorization Server's own default — `requireAuthorizationConsent(false)` — applies unconditionally to every `OAuthClient`, for every `Organization`. Confirmed live, not just read from the code: registering a real client and completing a real authorization request skips straight to redirect-with-code, no consent screen in between, regardless of what scopes the client requests or how sensitive they are.

This is a real product/security-policy decision, not a config oversight to silently flip — three questions had to be answered together:

1. **Should consent ever be shown at all?** Low risk today: JobSeeker, the one real consumer, is a trusted first-party client whose scopes are already known and expected by its own users (the same account holder registered with both systems knowingly). But `roadmap-and-release-plan.md` §2's own OpenID Foundation conformance exit criterion implicitly assumes a real, working consent flow exists to be tested — a suite that probes consent behavior would find a page that structurally never renders, an asterisk on that metric nobody had connected to this finding until this review.
2. **If shown, is it global (on/off for the whole system) or per-client?** A global switch is the simpler build, but it's the wrong shape for what this system actually is: a multi-tenant IdP where "trusted first-party" (JobSeeker today) and "an unknown third-party the end user has never heard of" (any future second consumer) are both real, simultaneously-possible cases the moment a second `Organization`'s clients diverge in trust level. A global flag can't express both at once; a per-client one can.
3. **What's the default for a client that doesn't say?** The two failure directions aren't symmetric: defaulting to no-consent-required (today's de facto behavior) means every new client is implicitly pre-authorized until an operator remembers to turn consent on — the exact silent-widening shape this register keeps finding and closing elsewhere (TD-SEC-010, TD-SEC-019). Defaulting to consent-required means an operator has to make one deliberate, auditable choice (`requireConsent: false`) to grant a client the friction-free path — the same "secure by default, explicit opt-out" shape ADR-0013 already chose for confidential-clients-only.

## Decision

**Consent requirement is a per-client attribute (`oauth_clients.require_consent`), defaulting to `true` for every new registration.** An operator registering a trusted first-party client explicitly sets `requireConsent: false` in the registration request to skip the consent screen — a deliberate, auditable action, never an inherited silence. Every already-registered client is migrated to `require_consent = true` (the ALTER's own `DEFAULT true`, same "safe default on an ALTER, opt out per row" convention as TD-SEC-018's `platform_clients.active` column) rather than assumed to keep today's de facto no-consent behavior — an operator who wants JobSeeker's own client to stay frictionless has to make that call explicitly, once, not have it made for them by this migration.

`OrganizationRegisteredClientRepository.toRegisteredClient(...)` now wires `ClientSettings.builder().requireProofKey(true).requireAuthorizationConsent(client.requireConsent()).build()` — the one line TD-SEC-026 found missing, now driven by real per-client state instead of a hardcoded value either direction. Spring Authorization Server's own unbranded `DefaultConsentPage` (TD-SEC-011, still open — no branding, no per-client display name/logo) is what actually renders; TD-SEC-009's own CSP work already scoped a real, narrowly-relaxed policy for exactly this page, live-verified now that the page genuinely renders instead of staying dormant.

No new endpoint, no Thymeleaf template owned by this project — the whole implementation is one `ClientSettings` line plus the schema/domain/use-case plumbing to carry the per-client flag end to end (`oauth_clients.require_consent` → `OAuthClient.requireConsent()` → `RegisterOAuthClientCommand`/`Request` → `ClientSettings`). Consistent with ADR-0003/ADR-0001: build the product on top of Spring Authorization Server, never reimplement its protocol surface.

## Consequences

- **Positive:** closes the real gap TD-SEC-026 named — a consumer application requesting sensitive scopes from a less-trusted `Organization` can now actually show the end user what it's asking for, and the OpenID Foundation conformance suite (`roadmap-and-release-plan.md` §2) now has a real consent flow to exercise instead of a structurally-dormant page.
- **Positive:** matches this system's own multi-tenant shape — trust is a property of a specific client relationship, not a system-wide constant, so the mechanism controlling it has to be per-client too.
- **Positive:** secure by default without breaking today's one real integration — a fresh registration is safe by construction; JobSeeker's own already-registered client needs one explicit, operator-driven, auditable update to `requireConsent: false` if frictionless login is still wanted for it (a decision left to the operator, not made silently by this ADR).
- **Negative:** the consent screen an end user actually sees today is still SAS's own unbranded default (TD-SEC-011, unchanged by this ADR) — a real users sees a generic "Consent required" page with no Clavaris or consumer-application branding until ADR-0009's embedded/branded login work happens.
- **Negative:** one more per-client knob an operator has to understand and set correctly at registration time — mitigated by defaulting to the safe value, so getting it wrong in the dangerous direction requires an explicit, visible choice rather than an omission.

## Alternatives considered

- **A single global on/off switch for the whole system.** Rejected: cannot express "JobSeeker trusted, a future second consumer not" at the same time — the exact scenario this system is built to eventually support (ADR-0010, multiple independent `Organization`s with materially different trust levels).
- **Default new clients to `requireConsent: false` (today's de facto behavior), require an explicit opt-in to turn consent on.** Rejected: repeats the same silent-widening shape this register has already found and closed twice (TD-SEC-010's unconditional exception, TD-SEC-019's plaintext bearer tokens) — a security-relevant default should fail toward showing the user more, not less, absent a deliberate decision otherwise.
- **Per-scope sensitivity (e.g., `openid`/`profile` silent, anything else prompts) instead of per-client.** Rejected for v1: no scope catalog exists yet to hang a sensitivity tier on (TD-ARCH-004, still open) — building one is a bigger, separate decision, and per-client consent already covers the real, present need (JobSeeker vs. an unknown future consumer) without it. Revisit once TD-ARCH-004 exists and a second consumer's actual scope requests give this a real case to design against.
