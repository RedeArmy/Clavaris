## 0. Purpose and how to read this

This is a working engineering register, not a status report for the sake of one. Its job is narrow: separate three things that are easy to conflate at this stage of a project, and that get more expensive to untangle the longer they're left conflated —

1. **Technical debt** — code or design decisions already shipped that carry a known rework cost, a known risk, or a known correctness gap, accepted deliberately in exchange for speed. This is the actual subject of this document (§2–§3).
2. **Anticipated debt** — not yet incurred, but predictable given the current architecture's trajectory: a decision made today that we already know will need revisiting once a specific, nameable future condition is met (§3).
3. **Backlog / deferred scope** — features not yet built because they're sequenced later, not because a shortcut was taken. This already has a home — `docs/01-product/roadmap-and-release-plan.md` — and is only referenced here (§4), never duplicated, so this register doesn't quietly turn into a second, drifting copy of the roadmap.

**Framing for an early-stage project:** almost none of this is alarming in isolation. `identity-module` didn't exist three weeks ago; the count of real user accounts in any environment is zero. The right reaction to this document is not "why does an early-stage project have debt" — every project this young that *doesn't* have a list like this hasn't looked hard enough. The right reaction is: does the sequencing in §5 make sense, and does anything here get worse the longer it's left alone. Several items do — those are flagged explicitly.

**Severity scale** (calibrated to this project's own stated bar — "zero critical/high findings open at launch," external security review is a hard gate, not optional):

| Severity | Meaning |
|---|---|
| **P0** | Must close before the external security review gate can even be scheduled, or is a live correctness bug today (not a missing feature — something that already misbehaves) |
| **P1** | Must close before v1 exit criterion (`roadmap-and-release-plan.md` §2) is credible — real consumer traffic depends on it |
| **P2** | Should close before scaling past the current single-operator, single-consumer, low-traffic stage — will bite at the next stage, not this one |
| **P3** | Known, accepted, low-cost-to-defer — correct to leave alone for now, tracked so it isn't rediscovered from scratch later |

**Lifecycle** — every row in §2/§3 carries a `Status` and a `Date`. `Date` is the date of the *last status transition*, not when the row was first written — it moves forward every time `Status` changes, so at a glance "how long has this actually been sitting in its current state" is answerable without digging through git blame.

| Status | Meaning |
|---|---|
| **Pending** | Identified and recorded. Nobody has started looking at it yet. Every new row starts here. |
| **Analyzed** | Investigated — root cause confirmed, a concrete remediation approach chosen (and, where useful, noted in the row itself). Not fixed yet. |
| **Resolved** | Fixed and verified. The row is moved out of §2/§3 into §6 (Closed Technical Debt) with a resolution note and reference (commit/PR) — never deleted, so there's a permanent record of what the debt was and how it was actually closed, not just that it's gone. |

## 1. Executive summary

Clavaris's actually-shipped surface today is: account registration, password authentication, email verification and password recovery (real delivery via Resend, ADR-0011 — closing TD-SEC-004), the full interactive Authorization Code + PKCE flow with real login, refresh tokens with single-use rotation and reuse detection (BR-ID-03 — `test-strategy.md` §3's own "single highest-value security invariant in the system," now built directly on real persistent state rather than debt that would have needed redoing, per TD-FUT-001's own preempted sequencing concern), `client_credentials` for the platform and management-API tiers, and full per-`Organization` tenant isolation (issuer, JWKS, client registry). All of it is tested end-to-end against real Postgres and real cryptographic signature verification — the engineering discipline behind what exists is genuinely high, and that's exactly why this register is short on "sloppy code" findings and long on "infrastructure that's provisioned but has zero consumers" and "correctness invariants the project's own docs already named as highest-priority that haven't been started yet."

Three findings dominated the risk picture and shared a root cause worth naming once, not eight times below: **almost all durable server-side state in this system — signing keys, OAuth2 authorization codes, HTTP sessions, rate-limit counters (once they exist) — used to live only in the JVM's own memory**, even though Redis is already declared as a dependency and running in `docker-compose.yml`. Two of those are now closed: signing keys (platform and per-Organization alike) persist to a real, restart-surviving PKCS12 file (**TD-SEC-002**), and every SAS-managed authorization/token record — authorization codes, access tokens, refresh tokens, ID tokens, for both tiers — persists to real Postgres via SAS's own `JdbcOAuth2AuthorizationService` (**TD-SEC-003**, see §6 for both). A routine deploy no longer mass-invalidates every issued token, and closing TD-SEC-003 directly surfaced and closed a second, previously-latent gap in the same pass (**TD-SEC-010** — `RegisteredClientRepository.findById`, unreachable until something finally called it, then a real 500 in two integration tests until fixed). Rate-limit counters are now closed too (**TD-SEC-001**, see §6) — Redis has its first real consumer in the codebase, a genuine atomic fixed-window limiter, not a placeholder. **HTTP sessions are now closed too (TD-ARCH-002, see §6)** — Spring Session backs every `HttpSession` with real Redis, closing the last of the three "state only lived in JVM memory" gaps this section originally named, and directly unblocking horizontal scaling (TD-FUT-004, also closed, see §6). One related, narrower gap in the same family surfaced and closed alongside it: SAS's own `JdbcOAuth2AuthorizationService` stored every bearer token value in `oauth2_authorization` as plaintext, not a hash — the one table in this schema `data-model.md` §2's "only a hash is ever persisted" principle hadn't reached yet, because it wasn't this project's own design to begin with (SAS's, ADR-0003). A wrapping `HashedTokenOAuth2AuthorizationService` now HMAC-SHA256-hashes every authorization code/access token/ID token value before it reaches Postgres, restoring the raw value in memory only for the exact token slot SAS's own revocation/introspection providers immediately re-compare it against (**TD-SEC-019**, see §6).

A dedicated security-auditor pass (2026-08-20, TD-SEC-012–017) found a second, unrelated class of gap on top of that: not missing infrastructure, but a real, exploitable defect in code already merged and passing its own tests. `SpringSecurityAuthenticatedSessionEstablisher` established the post-login session by hand, bypassing Spring Security's standard authentication filter chain entirely — which meant the session-ID-regeneration defense against session fixation (CWE-384) never ran. This was the one item in the whole register that wasn't "not built yet" or "not hardened yet" — it was a live vulnerability in the shipped login flow. **Closed same-day (TD-SEC-012, see §6)**, ahead of every other item in §5's sequencing, precisely because it had zero dependency on anything else and the cost of leaving it open kept compounding (TD-FUT-008). The same pass also found the local-dev Docker profile silently activated by default when unset — **also closed, TD-SEC-013, see §6.** The codebase's near-zero security-event logging outside one bootstrap class is now **fully closed** for every event with a real, already-shipped feature behind it: `AuthenticateWithPasswordService` logs every login success/failure (TD-SEC-014), `TokenIssuanceEventLogger` logs every access/ID token either issuer tier mints (TD-SEC-016), and `TokenRevocationEventLogger` logs every `/oauth2/revoke` call — plus the logs themselves are now real Elastic Common Schema JSON, not just grep-able text (TD-SEC-017, which also delivered the first-ever test coverage of the revocation endpoint, previously completely unexercised). Password-reset event logging (TD-FUT-009) is now closed too, delivered alongside TD-SEC-004 once the feature itself existed — every event `nfr-quality-attributes.md` §5 names now has a real log line behind it.

A dedicated follow-up review of the rate-limiting feature itself (2026-08-23, TD-SEC-022/023, TD-TEST-003, TD-FUT-010/011/012, TD-PROC-003) found the same shape of gap this register keeps finding on otherwise well-built features: the code does exactly what its own tests prove and nothing has been asked about the conditions those tests don't exercise. Concretely — nothing defined what happened to every login/token/dashboard endpoint across all three tiers if the single, non-HA Redis container was ever unreachable (**TD-SEC-022**); and two of the three security chains carrying rate-limit rules (the platform `client_credentials` tier and the whole `/platform/**` dashboard tier) had only ever been proven correct by unit tests that mock `RateLimiter` and construct the filter directly, never by an HTTP-level test proving the filter is actually on the real chain in the real order (**TD-TEST-003**) — exactly the class of bug (a same-anchor `addFilterAfter` collision, see TD-SEC-001's own closure note) that integration coverage on the one chain that has it already caught once. **Both closed same-day, see §6**: Redis now fails open with a real, live-verified test against a genuinely dead connection, and a new `PlatformTierRateLimitingIntegrationTest` proves all 6 previously-uncovered rules.

Both incident-response runbooks named as launch-blocking gaps since the original threat model are now written (TD-SEC-005, TD-SEC-006, see §6) — and written honestly against what the system can actually do today, not the eventual ADR-0010 design, which at the time still diverged from it in ways that mattered mid-incident (no per-tenant key-rotation endpoint existed yet; a full restart was the only containment lever, and it wasn't scoped to one tenant). Writing the `PlatformClient` runbook specifically surfaced a new gap this register didn't have: there was no self-service way to revoke or rotate the single highest-value credential in the system at all — only raw SQL against production (**TD-SEC-018**). Exactly the kind of finding a real incident-response exercise is supposed to catch before an actual incident does — **and, along with the per-tenant key-rotation endpoint the same paragraph named as missing (TD-SEC-008) and the audit-logging capability both of them depend on to be worth anything (TD-SEC-007), all three closed 2026-08-23, see §6.** Both runbooks themselves are now measurably more true than the day they were written, not just written.

A dedicated SDE-III review (2026-08-26), deliberately scoped to the whole codebase rather than re-checking the last several passes' own work, found two real security gaps neither prior pass had reason to look for: the account/organization-deletion work just shipped exposed that **no revocation call site in the tenant `Account` tier's own chain — password reset, refresh-token reuse detection, account deletion, organization deletion — ever invalidates a live `HttpSession`** (TD-SEC-031), even though the exact right pattern already exists and works correctly for the `PlatformAccount` tier; and that **the entire `/api/v1/admin/**` management API, now including two genuinely destructive endpoints, has zero rate limiting** (TD-SEC-030), a gap that existed before this week but only became consequential once organization-level hard-delete existed to be abused through it. A third, much smaller finding (TD-ARCH-007) is a real but currently-inert inconsistency between the two new deletion services. None of these are code-quality findings — the deletion work itself is solid, 100%-covered, live-verified — they are gaps in what got asked of it, the same shape almost every prior finding in this register has taken.

**All three closed the same day, see §6.** TD-SEC-031's own fix is the more interesting story of the three: the first version — a new `AccountSessionRevoker`/`AccountSessionRevokerBridge` pair, plus the missing `ConcurrentSessionFilter` wiring `OrganizationAuthorizationServerConfig` needed for `expireNow()` to have any effect at all — broke a real, already-passing integration test the moment it was added. `DeleteAccountIntegrationTest` caught a genuine regression live: a browser revisiting the (`permitAll()`) login page with an already-revoked session cookie hit Spring Security's own default terminal "session expired" response instead of a fresh login form, because `ConcurrentSessionFilter` doesn't distinguish "this session is expired and the resource is protected" from "this session is expired and the resource is the login page itself." Root-caused by bisection (removing the new filter wiring made the test pass again, confirming causation before writing a fix) rather than patched blind, and fixed properly with a custom `SessionInformationExpiredStrategy` that invalidates the stale session and lets the request continue, not by weakening the test or reverting the security fix. TD-SEC-030 (admin-API rate limiting, keyed per-`PlatformClient`) and TD-ARCH-007 (organization-module's own `event_outbox` mirror, in its own separate `organization_event_outbox` table — a real, live-caught naming collision avoided, not assumed) both closed the same pass without incident.

A dedicated SDE-III performance/concurrency review (2026-09-06), the first pass to deliberately look for optimization and bottleneck findings rather than security ones, found a consistent shape across five new rows (**TD-PERF-003 through TD-PERF-007**, all still open): the parts of this system that scale correctly are the ones a security- or correctness-focused review already forces careful attention onto (the Redis rate limiter's own atomic Lua script and fail-open design, webhook delivery's own per-call HTTP timeout — both read in full and confirmed already solid), while the parts nobody had reason to look at twice are running on unexamined framework defaults. The highest-leverage of the five (**TD-PERF-007**) is the one genuinely plausible full-outage risk in this list, not just a slow degradation: no HikariCP/Tomcat-thread-pool/JVM-heap/container-memory tuning exists anywhere against Argon2id's own deliberately expensive per-call cost sitting in the login hot path, confirmed by inspection rather than assumed. The rest are systemic-but-slow: a single-thread `@Scheduled` pool serializing all 11 background jobs in the app (**TD-PERF-003**, confirmed by decompiling the actual resolved `spring-boot-autoconfigure` jar's bytecode, not guessed from documentation), webhook delivery's own fully sequential per-batch dispatch compounding it (**TD-PERF-004**), an N+1 query pattern inside a lock-holding transaction in the outbox-to-webhook fan-out (**TD-PERF-005**), and two unbounded in-memory caches whose entries for since-deleted rows are never purged (**TD-PERF-006**). None of these are bugs at today's near-zero-traffic, single-operator stage — same framing TD-PERF-001/002 already established — and none required a design change to fix, only configuration and a small amount of targeted refactoring once real traffic makes them worth doing before, not after, the first incident names them.

A second SDE-III whole-codebase review (2026-09-06, same day, deliberately broader than the performance pass above — a four-agent fan-out across concurrency, DB/performance, resource-management, and code-quality lenses, with every agent instructed to read this register first and every finding independently re-verified against real source before being written here, not taken on an agent's word) surfaced **13 new rows** (**TD-SEC-051/052/053**, **TD-PERF-009 through TD-PERF-015**, **TD-ARCH-017/018/019**) — this pass itself was investigation and documentation only, at explicit request; all three **TD-SEC** rows, all seven **TD-PERF** rows (009-011 on 2026-09-06, 012-015 on 2026-09-07), and **TD-ARCH-017/018/019** (2026-09-07) were subsequently implemented and closed in separate follow-up passes the same week (see §6) — every row from this review is now closed. The single most consequential finding is **TD-SEC-051**: a real, traced race between signing-key rotation's own in-memory `KeyPair` cache and the Postgres advisory lock added on 2026-09-03 specifically to close a *different* rotation race — the lock correctly serializes which `kid` ends up active in the database, but never touches the unlocked in-memory write, so two concurrent rotations (an ordinary double-click, not adversarial timing) can leave the DB's active `kid` pointing at a different key than the one actually cached, silently breaking every token that Organization issues afterward until a later, non-racing rotation happens to realign the two. **TD-SEC-052** and **TD-SEC-053** are both real, if narrower, security gaps in the same "goes to great lengths in one place, misses an adjacent one" shape this register keeps finding: a deleted Organization's RSA private key outlives the Organization in both memory and on disk (the one place TD-SEC-029's own emergency-purge discipline doesn't reach), and webhook endpoint URLs are validated for scheme and shape but never checked against private/loopback/cloud-metadata address ranges — a classic, previously-undocumented SSRF gap reachable via the ordinary management API, not just the platform tier. The seven new `TD-PERF` rows split into two real classes: three availability-relevant missing-timeout/blocking-call gaps on hot paths external dependencies can stall (social-login's default Spring HTTP clients, Redis's implicit 60s Lettuce default, and a synchronous Resend call sitting directly in every login/passwordless-auth completion — **TD-PERF-009/010/011**), and four smaller, TD-PERF-005-shaped query-efficiency gaps (an unbounded webhook-history fetch, unbatched per-event outbox writes inside a lock-holding transaction, a redundant per-token-issuance DB round trip for data already cached, and roughly half the pre-session-establishment reads on the login path being outright duplicates of a query made moments earlier in the same request — **TD-PERF-012 through 015**). The three `TD-ARCH` rows are minor, P4 documentation-drift/duplication findings, not design flaws. Every category this pass looked at and found genuinely clean is recorded in the rows' own "checked and found clean" reasoning, not just the findings — including, notably, that this codebase's own singleton/mutable-state discipline, broad-exception-catching discipline, and JPA index coverage are all confirmed strong across all five modules, not merely assumed to be.
