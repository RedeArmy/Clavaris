## 0. Purpose and how to read this

This is a working engineering register, not a status report for the sake of one. Its job is narrow: separate three things that are easy to conflate at this stage of a project, and that get more expensive to untangle the longer they're left conflated —

1. **Technical debt** — code or design decisions already shipped that carry a known rework cost, a known risk, or a known correctness gap, accepted deliberately in exchange for speed. This is the actual subject of this document (§2–§3).
2. **Anticipated debt** — not yet incurred, but predictable given the current architecture's trajectory: a decision made today that we already know will need revisiting once a specific, nameable future condition is met (§3).
3. **Backlog / deferred scope** — features not yet built because they're sequenced later, not because a shortcut was taken. This already has a home — `docs/01-product/roadmap-and-release-plan.md` — and is only referenced here (§4), never duplicated, so this register doesn't quietly turn into a second, drifting copy of the roadmap.

**Framing for an early-stage project:** almost none of this is alarming in isolation. `identity-module` didn't exist three weeks ago; the count of real user accounts in any environment is zero. The right reaction to this document is not "why does an early-stage project have debt" — every project this young that *doesn't* have a list like this hasn't looked hard enough. The right reaction is: does the sequencing in §5 make sense, and does anything here get worse the longer it's left alone. Several items do — those are flagged explicitly.

**Severity scale** (calibrated to this project's own stated bar — `CLAUDE.md` §6: "zero critical/high findings open at launch," external security review is a hard gate, not optional):

| Severity | Meaning |
|---|---|
| **P0** | Must close before the external security review gate can even be scheduled, or is a live correctness bug today (not a missing feature — something that already misbehaves) |
| **P1** | Must close before v1 exit criterion (`roadmap-and-release-plan.md` §2) is credible — real consumer traffic depends on it |
| **P2** | Should close before scaling past the current single-operator, single-consumer, low-traffic stage — will bite at the next stage, not this one |
| **P3** | Known, accepted, low-cost-to-defer — correct to leave alone for now, tracked so it isn't rediscovered from scratch later |

**Lifecycle** — every row in §2/§3 carries a `Status` and a `Date`. `Date` is the date of the *last status transition*, not when the row was first written — it moves forward every time `Status` changes, so at a glance "how long has this actually been sitting in its current state" is answerable without digging through git blame.

| Status | Meaning |
|---|---|
| **Pending** | Identified and recorded. Nobody has started looking at it yet. Every new row starts here. |
| **Analyzed** | Investigated — root cause confirmed, a concrete remediation approach chosen (and, where useful, noted in the row itself). Not fixed yet. |
| **Resolved** | Fixed and verified. The row is moved out of §2/§3 into §6 (Closed Technical Debt) with a resolution note and reference (commit/PR) — never deleted, so there's a permanent record of what the debt was and how it was actually closed, not just that it's gone. |

## 1. Executive summary

Clavaris's actually-shipped surface today is: account registration, password authentication, the full interactive Authorization Code + PKCE flow with real login, `client_credentials` for the platform and management-API tiers, and full per-`Organization` tenant isolation (issuer, JWKS, client registry). All of it is tested end-to-end against real Postgres and real cryptographic signature verification — the engineering discipline behind what exists is genuinely high, and that's exactly why this register is short on "sloppy code" findings and long on "infrastructure that's provisioned but has zero consumers" and "correctness invariants the project's own docs already named as highest-priority that haven't been started yet."

Three findings dominate the risk picture and share a root cause worth naming once, not eight times below: **almost all durable server-side state in this system — signing keys, OAuth2 authorization codes, HTTP sessions, rate-limit counters (once they exist) — currently lives only in the JVM's own memory**, even though Redis is already declared as a dependency and running in `docker-compose.yml`. Nothing in the codebase talks to it yet. This is not eight independent bugs; it's one architectural gap (no distributed state layer wired up) with eight symptoms. Closing it once (§2, TD-ARCH-002 and its cross-references) is cheaper than discovering each symptom separately in production.

## 4. Explicitly out of scope for this register (backlog, not debt)

Named here only so nobody mistakes "not in the table above" for "forgotten." These are deliberately sequenced-later features, not shortcuts taken against them — tracked in full in `roadmap-and-release-plan.md`, not duplicated here: MFA (v1.1), password reset flow, social login (Google/GitHub), account-deletion API, webhook delivery (`webhook-module`), self-service client registration console, embedded/branded login (ADR-0009), SAML/SCIM (v2). If work starts on any of these and a genuine shortcut gets taken along the way, *that* shortcut belongs back in §2 — the feature not existing yet does not.

## 5. Recommended sequencing

Not a commitment, a professional opinion on order — final call on scheduling stays with the roadmap owner.

1. **Close the shared root cause first (TD-SEC-002, TD-SEC-003, TD-ARCH-002)** — wiring an actual distributed/persistent state layer (Redis for sessions and rate-limit counters once built; a real, restart-surviving `TOKEN_SIGNING_KEY_STORE_PATH`-backed store; and an explicit, persistent `OAuth2AuthorizationService`) closes three P0/P1 items and pre-empts TD-FUT-001 and TD-FUT-004 from ever needing to be discovered the hard way.
2. **Fix TD-SEC-004 (the false "email sent" message) immediately, independent of everything else** — it's a live correctness bug a real user could hit today, and the fix (either wire real email delivery, or stop the UI from claiming it happened) is small next to the items above it.
3. **Write the two incident-response runbooks (TD-SEC-005, TD-SEC-006)** — pure documentation, no code dependency on anything else in this list, and both are named as launch-blocking today.
4. **Rate limiting (TD-SEC-001)** naturally follows step 1 once Redis has a real consumer in the codebase.
5. **Ratify ADR-0010 (TD-PROC-001)** — costs nothing but a review pass, and leaves the project's most-depended-upon decision in a materially less defensible state the longer it stays "Proposed."

Everything else in §2/§3 can reasonably wait for its own natural trigger condition without actively getting worse in the meantime.
